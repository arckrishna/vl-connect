Streaming Window Metrics Aggregator

Integrated with a Library Management System

Real-time event processing · Window-based analytics
01

Technical Feasibility

The project is technically feasible using Python, a cloud message broker, Redis, FastAPI, and web technologies.

The Library Management System generates events whenever a book is issued, returned, or reserved. These events are transmitted through either CloudAMQP (RabbitMQ) or AWS Kinesis Data Streams to the Python stream processor.

The processor implements tumbling and sliding windows to calculate metrics. Redis stores the aggregated results, which are retrieved through FastAPI and displayed on a real-time dashboard.

The required technologies and development tools are available for implementation and testing. The project can be implemented using established technologies.

02

Economic Feasibility

The project can be developed at a low cost using open-source software and free-tier services where available.

  • Python, FastAPI, Redis, and Docker can be used without software licensing costs.
  • CloudAMQP offers a free plan subject to usage limits.
  • AWS Kinesis may incur charges depending on configuration and usage.
  • Development and testing can be performed on an existing computer.
Therefore, the project is economically feasible if cloud usage is monitored and kept within the available budget.
03

Operational Feasibility

The system is designed to operate alongside the Library Management System. It automatically processes library events and updates metrics without requiring manual calculations.

The dashboard allows users to monitor book issues, returns, reservations, and event counts over selected time windows. Its web-based interface makes the results easy to understand and access.

The system can operate as a monitoring component without replacing the existing library application's core functions.

04

Schedule Feasibility

The project can be completed within the academic project timeline by dividing development into the following stages:

  1. 01Design the system architecture and data flow.
  2. 02Configure the cloud message broker and Redis.
  3. 03Implement event consumption and windowing logic.
  4. 04Develop the aggregation module and REST API.
  5. 05Build the monitoring dashboard.
  6. 06Perform functional testing, fault-injection tests, and performance benchmarking.
  7. 07Document the implementation and results.

Development can proceed module by module, allowing individual components to be tested before integration.

05

Risk Feasibility

Potential risks and mitigation strategies include:

RiskMitigation
Broker connection failureImplement reconnection and retry logic.
Duplicate eventsUse unique event IDs and deduplication.
Processor crashUse checkpoints and recover processing state where implemented.
Redis data lossConfigure persistence or reconstruct metrics by replaying retained events where supported.
High event volumeMeasure processing latency and optimize window processing.
Cloud cost overrunMonitor usage and remove unused cloud resources.

These measures can reduce the impact of failures, although complete fault tolerance will depend on the implementation and testing.

06

Conclusion

The Streaming Window Metrics Aggregator is technically, economically, operationally, and schedule-feasible as an academic project.

It combines cloud-based event delivery with real-time window processing and in-memory metric storage to monitor Library Management System activities. Using a modular architecture, suitable testing, and cost controls will support reliable implementation within the project scope.
