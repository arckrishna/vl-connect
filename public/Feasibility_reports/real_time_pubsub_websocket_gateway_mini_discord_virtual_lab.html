01

Introduction

The project designs a Real-Time Pub/Sub WebSocket Gateway as a Mini Discord backend, using a cluster of stateful WebSocket gateway nodes and a Redis Pub/Sub backplane.

Users connect through a Network Load Balancer to one of several gateway nodes. Each gateway manages connections, authentication, channel subscriptions, message routing, presence and heartbeats. When a message is published, Redis forwards it to every gateway, and each gateway delivers it to its own locally connected subscribers.

Durable data such as users, channels and message metadata lives in a separate SQL database, and media files live in object storage.

Because building and load-testing real infrastructure needs cloud accounts and cost, Phase 1 of the project is delivered as a design plus an interactive browser-based simulator, the Distributed Systems Virtual Lab, where the same architecture can be assembled, loaded with traffic, broken with failures and observed.

02

Layer Descriptions

Client

Web, mobile, desktop and IoT clients open a wss:// connection and send requests such as:

  • Connect and authenticate
  • Subscribe to a channel
  • Publish a message
  • Receive messages and send heartbeats

Network Load Balancer

The only internet-facing component. It routes TCP / WebSocket connections to healthy gateway nodes. A connection stays on the node that accepted it.

WebSocket Gateway Cluster

The custom layer. There are N gateway nodes (GW-1 to GW-N), scaled by an Auto Scaling Group on active connections. Each node contains:

Connection ManagerMaintains client connections
Authentication & Rate LimitingValidates access and controls request rates
Channel / Room ManagerMaintains subscriptions
Message RouterRoutes messages to local subscribers
Presence ManagerTracks user presence
Heartbeat HandlerDetects and cleans dead connections

Redis Pub/Sub Backplane

Redis Enterprise / ElastiCache stores data temporarily and forwards events between gateways. Example flows:

  • Gateway → Redis Pub/Sub → all other gateways (message fan-out)
  • Gateway → Redis → session and presence map (user to node)
  • Gateway → Redis → subscription registry (channel to nodes/users)
  • Gateway → Redis → rate-limit counters
Important limitation: Redis Pub/Sub is transient: it keeps no history and does not replay messages.

Supporting Services

  • Auth Service: login, registration, JWT issuance and validation.
  • REST API Service: server and channel CRUD, user profile, history and metadata.
  • Media Service: uploads to S3, URL generation. Only links and metadata travel in messages.

Persistent Storage

  • SQL Database (Aurora / RDS): users, servers, channels, roles, message metadata.
  • Object Storage (S3): avatars, attachments, media files.

Background Workers (Control Plane Tasks)

Presence expiry cleaner, offline message processor, metrics aggregator, audit and logging worker, health monitoring.

Phase 3 – Editor and Live Metrics

Feasibility

Technical: React, TypeScript, Vite, Tailwind, React Flow, Zustand, Recharts and Vitest are sufficient to implement the editor, simulation engine, charts and tests. The architecture itself uses mature managed services (NLB, ElastiCache, Aurora, S3).

Implementation: Seven phases, with the first five complete, make development and testing simple. The engine has no UI dependency and is tested on its own.

Resource: Development and testing run locally in the browser with Node.js 20.19+ and npm. No server is needed.

Cloud: Phase 1 needs no cloud account. Live infrastructure on AWS is deferred to Phase 6.

Failure Testing: Failures are injected in the simulator while it runs, so no real service has to be stopped. Each failure is repeatable with the same seed.

Cost: Open-source tools only; Phase 1 has no cloud cost. Cloud spend in Phase 6 is limited by running a small pilot only when needed.

Fan-out: Redis Pub/Sub provides low-latency fan-out. Its limit is one operation per published message, which the simulator shows as a possible bottleneck when Redis is undersized.

Limitations: Capacities and latencies are illustrative defaults, not measured AWS or Redis limits. The model uses fluid batches, so there are no per-packet effects.

Expected Outcome

The final system demonstrates how a chat application can serve many concurrent users through multiple gateway nodes while Redis fans messages out between them.

With the default seed (42), the lab shows a healthy baseline of about 100 messages/s completed and 2,000 deliveries/s with P99 latency near 78 ms; saturation under overload at about 390 messages/s completed with errors near 35% and P99 near 2 s; local delivery continuing during a Redis outage with a delivery ratio near 33%; and a crashed gateway's 200 clients reconnecting to the surviving gateways after the 3 s health-check delay.

These values come from the simulation engine and are illustrative, not measured.
