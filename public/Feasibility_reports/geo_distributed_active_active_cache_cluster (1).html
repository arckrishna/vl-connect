Executive summary

Group 03 is feasible for a student team if the cluster is built as a tested core library plus a deterministic multi-region simulator, with one short real multi-region run used only to calibrate and validate it. A permanent three-region cloud deployment is possible but poor value: it costs money, makes latency hard to repeat, and adds little to what the study must show.

The study rests on two ideas. A consistent hashing ring spreads keys over nodes and moves few of them when nodes join or leave. CRDTs let every region accept writes and still converge after conflicts or network partitions. Both are well documented and take a few hundred lines each; the hard parts are replicating across independent rings, clock skew and metadata growth, which this plan scopes carefully.

Problem statement and objectives

A cache that serves users on several continents faces a trade-off: route every write to one primary region and remote users wait a full cross-region round trip, or accept writes everywhere and handle conflicting updates to the same key. Group 03 asks for the second option, called active-active, built on multi-region cloud VMs connected by inter-region peering.

Two mechanisms make it work. Inside each region, a consistent hashing ring decides which node owns which key, so adding or removing a node moves only a small share of keys. Between regions, CRDTs (conflict-free replicated data types) merge concurrent updates deterministically, so replicas converge without a coordinator or a global lock.

The project must demonstrate the following, each of which can be tested:

Minimal key movement. Adding one node to an N-node ring remaps roughly 1/(N+1) of keys, and virtual nodes keep the load spread even.

Local writes. A write is acknowledged by the local region without waiting for any remote region.

Convergence. After a partition heals, all regions hold identical state for every key.

No lost updates for CRDT types. Concurrent increments and set additions are all preserved, while the same workload on a last-write-wins register visibly loses updates.

Observability. A learner can run each experiment in the virtual lab and see why the system behaved as it did.

Technical feasibility

Six of the eight components are standard techniques a student team can build and test; two (TTL under merge and delta-state CRDTs) are research-grade and should be descoped.

Cross-region replicationEvery region holds every key; a key's owner in one region sends updates to that key's owner in each other region, so replication follows keys, not nodesMediumBuild

Anti-entropyShip recently changed keys on a timer, plus a periodic digest comparison to repair missed updatesMediumBuild
Partition and failure handlingWrites continue on both sides of a partition and merge on heal; a node loss triggers ring rebalanceMediumBuild, in simulation
Clocks for LWWLast-write-wins needs timestamps; a hybrid logical clock limits the damage of clock skew (Kulkarni et al., 2014)MediumBuild, with skew injection

Delta-state CRDTsSmaller messages by sending only the changed part of a valueHighDescope; send full state

Three issues need design attention rather than extra effort.

Ownership differs per region. Each region runs its own ring, so a node join in Mumbai must not change what Frankfurt believes about a key. Replicating by key avoids this.

Metadata growth. Counters grow with the number of regions, but OR-Set tags grow with the number of additions until tombstones are compacted. The study should measure and report this rather than hide it.

Last-write-wins is a choice, not a bug. Showing lost updates under LWW next to preserved updates under CRDT counters is a core teaching point, so the lab should offer both.

Proposed architecture

A write is acknowledged by the local region and then replicated to the owner of the same key in every other region, where CRDT merge resolves any conflict.

architecture · 3 layers, 4 regions

The picture reads top down: the lab controls the simulator, which holds four regions joined by simulated links. The simulator and the real run execute the same core library, and the real run only supplies measurements to calibrate the latency matrix.

The write path has three steps.

The client's region hashes the key, sends the write to that key's owner node in the region, and the owner applies it and acknowledges.

The owner marks the key as changed and, on a timer, sends the new CRDT state to the key's owner in each other region.

Each receiving owner merges the state into its own copy; a periodic digest comparison repairs any message that was lost.

Reads go to the local owner and return its merged state, so a read can be stale by up to one replication delay.

The simulator replaces the cloud in three places. It uses a latency matrix seeded from the measured round-trip times, it injects partitions by dropping messages rather than editing firewall rules, and it can run dozens of nodes that no student budget could host. The real run exists to show that the simulated numbers are not invented.

Two guardrails apply. The Free plan blocks surprise bills because the account closes when credits run out, but enabling some features, such as AWS Organizations, can move the account to the Paid plan. Accounts created before 15 July 2025 may follow older Free Tier rules, so each teammate should check which plan their account is on.

Recommendation and next steps

Go: build Group 03 as a tested core library plus a deterministic simulator and virtual lab, validated by one 48-hour run on four VMs that should cost about $3-4.

The work splits into three tiers. Tier 1 is the ring, the four CRDT types, replication and partition handling inside the simulator. Tier 2 adds the guided lab experiments. Tier 3 adds the real validation run and polish; skipping it still leaves a complete submission, provided the report states the limitation.

The first five actions:

Confirm with the instructor that a simulator-backed virtual lab satisfies the case study, and agree the success targets.

Fix team size, deadline and roles, and check which teammate has an AWS account eligible for sign-up credits.

Build the ring and the four CRDT types with property-based tests before any interface work.

Build the discrete-event simulator with seeded randomness, a latency matrix, and partition and clock-skew injection.

Time-box the lab interface to two weeks, then schedule the validation run with a budget alert and a teardown script.

Open questions: team size, deadline and the exact meaning of the virtual-lab deliverable are assumed in this document and need confirming.
