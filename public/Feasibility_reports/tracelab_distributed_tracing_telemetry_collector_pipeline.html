02

Executive Summary

TraceLab is a Distributed Tracing Virtual Lab for studying how telemetry generated by an application passes through a collector pipeline and reaches a trace backend. It models an instrumented service graph, OTLP transport, a load balancer, two collector replicas, a trace backend and explorer, and a separate collector self-monitoring path.

The learner is expected to change sampling, batching, queue capacity and failure conditions, run the simulation, and compare the resulting visibility and pipeline behaviour.

The project is technically feasible because the principal concepts map to established observability patterns: application instrumentation produces spans, OTLP transfers telemetry, and a Collector pipeline receives, processes and exports data. The main implementation risk is ensuring that the simulator represents queueing, drops, retries and failure recovery consistently and explains its limits.

03

Project Overview

Modern user requests often cross multiple services. A slow or failed request cannot reliably be explained from one service log because each component sees only part of the request. Distributed tracing records spans connected by trace and parent-span identifiers. Those spans must then be delivered, processed, buffered and exported by a telemetry pipeline. If the collector is overloaded or the backend becomes unavailable, observability data can be delayed or dropped.

Problem Statement

Design and evaluate a simulated telemetry collection pipeline that accepts spans from instrumented microservices, distributes traffic across collector replicas, applies sampling and batching, buffers and retries exports within bounded capacity, and exposes collection health through a separate metrics-monitoring path.

Aim

To study and simulate a distributed tracing and telemetry collection pipeline, understand how traces flow across microservices and OpenTelemetry Collectors, and evaluate the impact of sampling, batching, collector capacity and component failures on telemetry collection.

Objectives

  • Explain trace, span and parent-child relationships across the API gateway, order, payment, inventory and database components.
  • Model OTLP transport from instrumented services to a collector endpoint over gRPC or HTTP.
  • Compare a two-replica collector cluster behind a least-buffered load balancer.
  • Observe the effects of head-based sampling, batch formation and bounded queues on retained telemetry.
  • Inject overload or component failures and record queue utilisation, exported spans, dropped spans and recovery behaviour where the simulator exposes them.
  • Use collector self-monitoring signals to connect pipeline health to a monitoring dashboard.
  • Produce a reproducible observation table and a report that distinguishes simulated outputs from real deployment measurements.

06

Operational Feasibility

Operational feasibility is high for the current scope because the stated environment is a local browser simulation. The learner does not need to provision cloud VMs, configure production credentials or maintain an always-on service.

The lab should provide an experiment reset, help text, a clear distinction between the primary telemetry path and self-monitoring path, and a way to capture the selected configuration and output metrics.

  • Skills needed: basic distributed-systems concepts, reading a trace tree, interpreting counters and percentages, and following the lab procedure.
  • Operational control: reset the experiment between scenarios and preserve a run record containing configuration, timestamp, outcome and limitations.
  • Maintainability: separate simulation logic, visual state and explanatory text so that a visual change does not silently change the experiment model.

Economic Feasibility

For the local-simulation scope, the direct infrastructure cost is expected to be negligible beyond a computer and internet access for opening the lab. The supplied design does not require a permanent cloud deployment. Open-source observability components could be used in a later prototype, but real deployment would introduce hosting, storage, network, monitoring and maintenance costs that are outside this feasibility estimate.

12

Recommendation

Proceed with TraceLab as a local-simulation project.

Complete the built-in procedure and at minimum capture one baseline run plus controlled sampling and capacity/failure experiments. Use the architecture diagram and this feasibility study to explain why the pipeline components exist, but do not claim real deployment, measured production latency or zero-loss guarantees unless separate evidence is collected.

If more time is available, validate one scenario with a real OpenTelemetry Collector in a local container environment and clearly label it as a separate validation experiment.
