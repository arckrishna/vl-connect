System Design · Feasibility Report

Cross-Cloud Service Discovery Registry

A common registry for registering service instances, discovering them by logical name, and observing their health across provider-labelled environments.

Node.js · Express · HashiCorp Consul · Health Checks
01

Executive Summary

This report evaluates whether a Cross-Cloud Service Discovery Registry can be implemented and demonstrated as a System Design micro-project.

The system aims to provide a common place to register service instances, discover them by logical name, and observe their health regardless of the cloud-provider label associated with each instance.

The proposed prototype uses a browser-based dashboard, a Node.js/Express API, and HashiCorp Consul for the service catalog and health checks. A local payment-service process supplies a sample HTTP health endpoint. AWS, Azure, and GCP can be represented as provider metadata or simulated instances; such labels do not mean that real resources have been provisioned in those clouds.

Feasibility finding: the core single-machine prototype is technically feasible with readily available tools and moderate implementation effort. Feasibility depends on validating registration, discovery, health status, error handling, and duplicate-free display behavior. Production-grade multi-region operation, secure cross-cloud networking, and high availability are outside the minimum prototype scope. No performance or completion claims are made without executed tests.
02

Problem Statement and Objectives

Problem Statement

How can service instances associated with different cloud environments be registered and discovered through a common registry, while allowing applications and users to obtain current endpoint details and distinguish healthy services from unavailable ones without manually maintaining service addresses?

Objectives

  • Provide a dashboard to register, list, search, and inspect service instances.
  • Store each service's logical name, unique instance ID, address, port, provider metadata, tags, and health-check configuration.
  • Use Consul APIs for actual service registration and discovery.
  • Expose backend API endpoints through Node.js and Express.
  • Monitor registered endpoints using Consul health checks.
  • Handle invalid input, unavailable Consul, missing services, and failed requests clearly.
  • Separate live registry entries from sample/demo rows and calculate counts correctly.
  • Document repeatable local setup and testing steps.
  • Keep simulated cloud-provider labels distinct from actual cloud deployment.

The project can be implemented with a small number of well-understood components.

The frontend sends HTTP requests to the Express API. The backend validates request data and communicates with Consul. Consul stores service definitions and evaluates configured checks. The dashboard renders the resulting catalog and health information.

05

Proposed Service Registration Flow

  1. The user enters service details in the registry form.
  2. The browser sends a JSON request to POST /api/services/register.
  3. The backend validates required fields and normalizes the health-check path, port, interval, timeout, and tags.
  4. The backend calls Consul's service-registration API.
  5. The backend returns success only if Consul accepts the registration; errors are returned with a useful message.
  6. The frontend updates the table after confirmed success and avoids adding a false success row when the API fails.
Registry form→POST /api/services/register→Express validation→Consul registration→Confirmed UI update
06

Proposed Service Discovery Flow

  1. The user searches for a service by logical name.
  2. The frontend calls the backend discovery endpoint.
  3. The backend queries Consul for matching instances.
  4. The API returns instance IDs, addresses, ports, tags, and available health data.
  5. The frontend displays the actual results or a clear empty/error state.
Search by logical name→Frontend→Backend discovery API→Consul lookup→Instance details & health

Reliability, Consistency, and Security

The most important reliability rule is that the UI must not report a service as successfully registered until the backend confirms the Consul operation. Registration acceptance and health-check passing are separate conditions. A service may be registered while its health check is failing.

Risk / failure scenarioMitigation and verification
Consul unavailableReturn a clear API error and show a frontend connection message.
Missing or malformed fieldsValidate name, ID, address, port, path, and timing values before calling Consul.
Duplicate instance IDsUse the service ID as a stable key and define an explicit duplicate/update policy.
Health endpoint failsDisplay the real Consul check state; do not infer health from registration alone.
Stale or duplicate rowsRefresh from the live catalog and keep sample rows visibly separate.
Frontend CORS or network failureConfigure local CORS appropriately and show failed fetches clearly.
Untrusted service dataEscape or safely render text; do not inject raw user values into HTML.
Unauthorized access in productionAdd authentication, Consul ACLs, TLS, and network restrictions before any production use.

Security feasibility is high for a local classroom prototype with no sensitive data. Production use would require a separate security design, secrets management, authorization, encrypted communication, audit logging, and secure Consul configuration.

10

Performance and Scalability Feasibility

The registry pattern can reduce hard-coded service addresses and centralize metadata lookup. However, this local prototype does not by itself prove performance under high request rates or availability across multiple regions. Consul's deployment topology, network latency, number of registered instances, health-check frequency, and backend request volume all influence behavior.

  • Measure API response time and request success rate only after running repeatable tests.
  • Test lookup behavior with one instance and multiple instances sharing a logical service name.
  • Check that service health changes are reflected after the configured health-check interval.
  • Record observed results, environment, and test steps; do not invent throughput or latency numbers.
  • Treat real cloud networking, multi-region registry replication, and automatic failover as future evaluation items.

13

Feasibility Decision

Decision: GO for a bounded local academic prototype.

Technical feasibility is high because the core tools are available and the workflow is straightforward. Operational feasibility is moderate because the demo depends on several local processes and careful startup order. Economic feasibility is high for the local prototype because paid infrastructure is unnecessary. Production feasibility is not established by this report.

The GO decision is conditional on passing the core acceptance tests: registration through the backend, discovery from Consul, accurate health status, correct error handling, and duplicate-free frontend rendering. If these tests fail, the project should be described as in progress until fixes are verified.

15

Conclusion

The Cross-Cloud Service Discovery Registry is feasible as a System Design micro-project when scoped as a local prototype that demonstrates registration, discovery, and health monitoring through Consul.

The proposed architecture is affordable and implementable with common tools, while its most important risks—false health claims, duplicate data, and dependency failures—can be addressed through validation and repeatable tests.

The report intentionally separates planned capabilities from verified behavior. A passing final assessment should be based on observed test results rather than the presence of code or a successful startup message alone. Real cross-cloud deployment, high availability, security hardening, and production-scale performance remain outside the conclusions of this feasibility study.
