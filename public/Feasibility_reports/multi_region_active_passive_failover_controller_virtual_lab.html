SYSTEM DESIGN MINI PROJECT

FEASIBILITY STUDY REPORT

1. Introduction and Objective

This project designs a controller that monitors a primary region and a standby region. If the primary stays unavailable, the controller checks the failure, confirms that the standby is ready, prevents the old primary from accepting writes, and redirects traffic. It also records events and supports a controlled failback.

2. Problem Statement

A regional outage can stop an application from serving users. A simple automatic switch can also cause problems if the primary is only temporarily unreachable, the standby data is out of date, or both regions accept writes. The controller must confirm failures and switch regions safely.

3. Objectives and Scope

Monitor the health of both regions and use repeated checks before declaring a failure.

Check quorum, standby readiness, and replication lag before promotion.

Prevent split brain by fencing the old primary before the standby accepts writes.

Switch traffic, verify the new route, and record failover events.

Support recovery and controlled failback; handle network, routing, and standby failures.

Scope: The main demonstration will simulate two regions, health checks, traffic switching, event logging, and failure scenarios. Real DNS changes and real cross-region database promotion are optional extensions.

5. Feasibility Analysis

The project is feasible as a student prototype because the main parts can be built and tested separately. A local simulation avoids the cost of running real cloud regions. A production system would need extra work for cloud permissions, DNS behaviour, database promotion, and reliable fencing.

6. Requirements

Configure both regions and show their health and current roles. Use repeated checks to avoid switching on one failed probe.

Start failover only after the failure threshold and safety checks pass, including standby readiness and replication lag.

Fence the old primary before promoting the standby. Only one region may accept writes, and the new route must be verified.

Record decisions, errors, and timings. Support recovery, manual failover, and controlled failback.

7. System Architecture

The architecture separates client traffic from the controller. Clients reach the active region through the router. Health monitors report region status, while the controller checks the failure conditions, coordinates fencing and promotion, and records each decision. Database replication is handled separately from traffic routing.

8. Data and Control Pathways

Normal operation

Client → Router → Active Region API → Primary database. Database changes are replicated to the standby, and health agents continue checking both regions.

Failover

Detect repeated failures → confirm quorum → check standby health and replication lag → fence the primary → promote the standby → update routing → verify a test request → record the result.

Failback

When the old primary recovers, keep it as standby. Check its health, synchronize data, and switch back only through a controlled procedure.

9. Network Boundaries

Clients connect through the traffic router, not directly to the controller or databases.

The controller uses restricted health-check and routing-control connections.

Replication uses a protected connection, and the standby remains non-writable until promoted.

12. Limitations

The local demo shows controller logic and simulated route switching, not recovery from a real cloud-region outage.

DNS caching and database replica promotion can affect recovery time and data loss in a real deployment.

The project does not guarantee zero downtime or zero data loss. These need to be measured in a real or representative test.

13. Conclusion

The Multi-Region Active-Passive Failover Controller is feasible as a system-design mini project. It demonstrates health monitoring, failure confirmation, standby promotion, traffic switching, event logging, and controlled failback. The main goal is to make the switch safe and verifiable, not just fast. Real cloud failover would require further implementation and testing.
