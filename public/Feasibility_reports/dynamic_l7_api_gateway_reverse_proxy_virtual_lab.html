Feasibility Report · Topic 16

Dynamic L7 API Gateway & Reverse Proxy

A secure, dynamically configurable entry point for web, mobile and external clients accessing private backend services.

Cloud Compute Instances · Secret Manager
01

Executive Summary

The project proposes a Dynamic Layer 7 (L7) API Gateway and Reverse Proxy running on a cloud compute instance: a single entry point for web, mobile and external clients.

The gateway verifies JWTs (signature, expiry and claims), matches each request's path and method against routing rules, forwards it to the correct private backend, and returns the response. Administrators can add, change or remove routing rules without restarting the gateway. JWT signing keys, API credentials and sensitive settings are fetched from a cloud Secret Manager rather than being hard-coded.

The report evaluates technical, economic, operational, schedule, legal/security and risk dimensions. Its finding is that the project is feasible across all examined dimensions, can use low-cost or free-tier cloud resources, and can be completed in roughly 8 to 10 weeks by a small team.

Source report recommendation: Proceed with implementation. Main risks identified are hot-reload correctness, Secret Manager dependency and single-instance failure; the report proposes mitigations for each.
02

Introduction and Background

In a microservice architecture, clients would otherwise need to know the address of every backend service and each service would have to implement its own authentication. An API Gateway acts as the front door of the system.

Because it works at Layer 7 (the application layer), it can inspect HTTP-level details such as URL path, headers, method and tokens, which a Layer-4 (TCP-level) load balancer cannot do.

A reverse proxy accepts client requests on behalf of backend servers, forwards them, and relays the responses. Combining a reverse proxy with JWT verification and a dynamically reloadable routing table gives a lightweight, centrally managed security and routing layer.

03

Problem Statement

Directly exposing every backend service creates a larger attack surface, duplicated security logic, rigid routing, poor secret handling and weak failure handling. Each service may be reachable from the public internet; every service must validate tokens independently; moving a path can require reconfiguration and restarts; credentials in code or config files can leak; and clients must cope with backend failures individually.

A single, secure, dynamically configurable gateway is therefore required.
04

Objectives and Scope

Objectives

  1. Provide a single entry point for multiple backend services.
  2. Authenticate every request using JWT verification.
  3. Route requests dynamically using URL path and request properties.
  4. Reload routing configuration without restarting the gateway.
  5. Protect secrets through a Secret Manager.
  6. Handle backend, gateway and network failures safely.

In Scope

  • HTTPS termination and JWT validation (signature, expiry, basic claims).
  • Path-based routing (with optional header or method matching) to User, Product and Order services.
  • Validated hot reload of routing configuration with last-known-good fallback.
  • Timeouts, HTTP 401/503 error handling and structured logging.
  • Deployment on cloud compute instances, with multiple gateway instances for availability.

Technical Feasibility

Technical feasibility asks whether the system can be built with available technology and skills. The report rates the main components highly feasible, with careful testing required for hot reload.

Key Technical Design Decisions

  • Atomic routing-table swap: the router keeps a pointer to an immutable routing table. A reload builds a new table, validates it, and swaps the pointer in one operation, so in-flight requests are never served from a half-updated table.
  • Config stored outside the gateway: routing rules live in cloud storage or a config service, allowing administrators to change routes without logging in to the VM; every gateway instance picks up the same change.
  • Fail-closed authentication: if the secret cannot be fetched and no cached secret exists, authentication-dependent requests are rejected instead of falling back to hard-coded credentials.
  • Secret caching with refresh: JWT signing keys and API credentials are fetched at start-up and refreshed periodically.
  • Claims extraction: verified token claims, such as user ID or role, can support simple access rules or be passed to backends as trusted headers.
  • Timeouts everywhere: connect, read and overall request timeouts prevent indefinite waits.
  • Stateless gateway: no per-user session state is stored on the gateway, so instances can be added or removed freely.
Technical verdict: FEASIBLE.

Economic Feasibility

Economic feasibility asks whether the cost is justified and affordable. The report expects near-zero cost for a minimal setup using free-tier resources or student credits, and a small monthly amount for a recommended demonstration setup with two gateways, three backends and an optional load balancer.

Benefits include use of free open-source libraries, no software licensing fees, the ability to stop resources after demonstration, hands-on experience with gateway and cloud technologies, and reduced duplication of authentication logic in a real deployment.

Economic verdict: FEASIBLE with very low cost for an academic project.

Operational Feasibility

  • Administrator usability: routing changes are made in cloud storage or a config service; no code change or restart is needed.
  • Client transparency: clients call a single base URL; backend moves or replacements are invisible to them.
  • Deployment: the gateway is a single deployable binary or container and can be replicated across VMs.
  • Monitoring: structured logs record request ID, matched route, backend, status and latency; health-check endpoints support load balancers.
  • Maintainability: modular JWT, router, config-loader and proxy components can be tested and replaced independently.
  • Availability: multiple gateway instances remove the gateway as a single point of failure; failed backends return HTTP 503 without crashing the gateway.
Operational verdict: FEASIBLE.

Legal, Ethical and Security Feasibility

Legal and Licensing

  • Proposed libraries and tools use permissive open-source licenses such as MIT, Apache 2.0 and BSD.
  • No personal or sensitive real-world user data is required; test data will be synthetic.
  • Cloud usage must follow the provider's terms of service and the college's acceptable use policy.

Assumptions and Constraints

Assumptions

  • A cloud account with free-tier or student credits is available.
  • The team has access to a domain or can use the VM's public IP for HTTPS testing.
  • Backend services are simple mock services representing User, Product and Order functions.
  • JWTs are issued by an existing or mock identity provider; token issuance is outside the gateway's scope.

Constraints

  • Fixed academic deadline and part-time effort.
  • Limited cloud budget.
  • Demonstration-scale traffic only; not tuned for internet-scale loads.
15

Conclusion and Recommendation

The feasibility study finds the project feasible technically, economically, operationally, on schedule and in legal/security terms, with manageable risks.

The gateway provides a unified, secure entry point for cloud backend services, abstracting raw compute resources into a higher-level routing and authentication layer. Dynamic routing, JWT verification, secure secret management and robust failure handling improve reliability, security and maintainability.

Recommendation: The project is technically sound, economically affordable, operationally practical and achievable within the academic schedule. Proceed to design and implementation following the report's timeline.
