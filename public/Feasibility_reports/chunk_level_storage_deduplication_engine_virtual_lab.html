1. Executive Summary

This report assesses whether a chunk-level storage deduplication engine can be implemented and evaluated within a course micro-project. The proposed prototype uses Rabin-style content-defined chunking (CDC), SHA-256 content identifiers, a SQLite metadata index, a local filesystem chunk store, and deterministic file reconstruction. The original system design also envisions distributed storage, replication, multiple API instances, and continuously running maintenance workers; those features are not included in the proposed prototype.

Feasibility finding: the single-machine prototype is technically feasible using commonly available development tools, subject to bounded file sizes, sequential uploads, and explicit consistency and recovery safeguards. Distributed fault tolerance, high availability, and production-scale performance cannot be established by this prototype. This report proposes an evaluation plan; it does not claim that implementation, benchmarks, or verification have already been completed.

2. Problem Statement and Objectives

The main design challenge is balancing storage efficiency with reliable retrieval. A chunking algorithm must avoid unnecessary boundary shifts, while the metadata layer must preserve the exact sequence of chunks for each uploaded file. Feasibility therefore depends on correctness as much as on compression-like savings: a smaller storage footprint is not useful if a restored file differs from the original.

Traditional file-level backup can store a complete new copy after a small edit. Chunk-level deduplication aims to store only unique chunks and maintain references from each file version to its ordered chunks. CDC can preserve reuse after insertions that shift byte positions, unlike fixed-size chunking.

The feasibility study asks whether the proposed implementation can (1) produce deterministic chunk boundaries, (2) reuse identical content across files and versions, (3) reconstruct files byte-for-byte, (4) detect missing or corrupted chunks, and (5) quantify storage savings and processing overhead on a reproducible local benchmark.

3. Scope and Assumptions

The project deliberately prioritizes a measurable proof of concept over a distributed deployment. This reduces infrastructure cost and permits repeatable experiments on a single development machine. Results from this environment should be interpreted as evidence about the algorithm and local implementation, not about throughput or availability in a cluster.

4. Proposed Architecture and Technology Feasibility

The proposed upload pipeline reads input incrementally, identifies CDC boundaries, computes a digest for each chunk, checks the chunk index, and stores previously unseen content. Once required chunks exist, the metadata layer records the ordered chunk references and publishes the file as complete. Retrieval reverses this process, verifying each chunk before assembling and checking the entire file.

Suggested metadata schema: chunks(hash PRIMARY KEY, size_bytes, ref_count, state), files(file_id PRIMARY KEY, original_name, file_size, sha256, status), and file_chunks(file_id, position, chunk_hash). A separate ordered mapping is important because a file can contain the same chunk more than once. Reference counts must represent actual references, including repeated occurrences.

5. Consistency, Reliability and Security

A practical implementation must preserve two invariants: completed file records must reference existing verified chunks, and deletion must never remove a chunk referenced by another completed file. Because database transactions and filesystem operations cannot be committed as one atomic operation, reconciliation and conservative garbage collection are essential safeguards.

5.1 Upload and metadata consistency

SQLite transactions do not make filesystem writes atomic. The proposed safe sequence is: write each new chunk to a temporary path, flush and atomically rename it into the content-addressed store where supported, then commit file metadata and reference counts in one SQLite transaction after verifying required chunks exist. A crash may leave orphan chunk files; an on-demand reconciliation scan should identify and remove unreferenced objects only after confirming no active upload uses them. Durability after power loss requires additional filesystem-specific testing and is not guaranteed here.

5.2 Recovery and deletion

A failed upload should not publish a completed file record. A subsequent retry may reuse existing content-addressed chunks, but exact checkpoint-based resumption is not part of the minimum scope. Deletion removes file references transactionally; physical chunk removal occurs only after no references remain and a reconciliation/GC pass confirms eligibility. Tests must avoid deleting chunks still referenced by other files.

5.3 Integrity and limits

During restore, verify each retrieved chunk against its SHA-256 name and compare the reconstructed output with the stored whole-file SHA-256. SHA-256 offers strong accidental-corruption detection but does not replace authentication or authorization. File size limits, path sanitization, disk-space checks and input validation should be applied if an HTTP API is exposed. Hash collisions are assumed negligibly unlikely, not mathematically impossible.

6. Resource and Operational Feasibility

The prototype does not require dedicated servers or cloud services. The principal resource demands are temporary storage during uploads and reconstruction, disk operations for many small chunk files, and CPU time for rolling fingerprints and SHA-256 hashing. Streaming processing and bounded input sizes help keep memory usage predictable.

7. Economic and Performance Feasibility

A realistic feasibility decision must consider both the savings and their cost. Repeated or slightly edited files should produce higher reuse, whereas unrelated files may offer little benefit and can incur metadata overhead. Benchmarks should therefore compare workloads of different redundancy levels rather than reporting only the most favorable case.

Storage saved (%) = 100 × (logical input bytes − physical stored bytes) / logical input bytes. Deduplication ratio = logical input bytes / physical stored bytes. Define physical stored bytes in two ways: (a) unique chunk payload bytes, for algorithm comparison; and (b) total on-disk footprint including SQLite and filesystem overhead, for operational reporting. Use the same denominator convention for CDC and fixed-size comparisons.

Record chunk count, mean chunk size, unique chunk bytes, metadata bytes, upload time, restore time, throughput (MiB/s) and seconds/MiB. Measurements must specify hardware, operating system, dataset size, cache/warm-up policy and number of repetitions. Storage savings are workload-dependent and may be negative for small or nonredundant files once metadata overhead is included. Cloud cost savings are not estimated because no deployment pricing or workload evidence is available.

10. Feasibility Decision and Next Steps

The GO decision is conditional: the project is viable as a student prototype if the team can demonstrate deterministic chunking, byte-perfect reconstruction, safe reference handling and transparent benchmark reporting. Failure of these correctness criteria should block claims of successful implementation, even if measured storage savings appear attractive.

Decision: GO for a bounded single-machine proof of concept. Technical feasibility is high for the core deduplication and reconstruction path, operational feasibility is moderate with manual recovery and testing, and economic benefit remains unproven until measured. The implementation should proceed only with the stated consistency safeguards and transparent measurement definitions.

Completion evidence should include source code, schema/migration scripts, test logs, reproducible fixture-generation steps, measured benchmark tables, and a short demo showing repeat upload, edited-file reuse, restore verification and corruption detection. A later phase would be needed to assess concurrent uploads, distributed replication, failover, authentication, and real production cost.

11. Conclusion

The recommended approach is to build and validate the smallest reliable end-to-end system first, then add deletion, recovery and performance evaluation. This sequence keeps the project manageable while producing concrete evidence that can support or revise the initial feasibility assessment.

The proposed chunk-level deduplication engine is a realistic System Design Micro-Project when treated as a local prototype rather than proof of a distributed storage platform. Its value can be established through correct chunk reuse, verified reconstruction and measured savings on declared workloads. Until implementation and experiments are complete, these remain testable objectives—not achieved results.
