1. Project Overview

Context and stream processing architecture summary

The Streaming Window Metrics Aggregator processes continuous events generated by a Library Management System to monitor library activities in real time. Events such as book issuance, book returns, and book reservations are transmitted through a cloud message broker to a stream processor.

This project implements a real-time stream processing architecture consisting of a Library Management System event producer, a cloud message broker using either CloudAMQP (RabbitMQ) or AWS Kinesis Data Streams, a Python stream processor, and Redis for storing aggregated metrics.

The processor groups events into tumbling and sliding windows and calculates metrics such as event count, sum, average, minimum, and maximum where applicable. FastAPI exposes the results through REST endpoints, and a web dashboard displays the updated metrics.

The Library Management System serves as the realistic workload and case study; the primary subject of the project is the stream processing and window aggregation layer that enables real-time monitoring of library activities.

Continuous Streaming

Low-latency event delivery from application sources through cloud message queues.

Window Aggregation

Tumbling (non-overlapping) and Sliding (overlapping) window calculations.

In-Memory Store

Fast key-value access via Redis with REST endpoint serving via FastAPI.

2. Problem Statement

Challenges in high-frequency event monitoring

A Library Management System may generate numerous events when members issue, return, or reserve books. Processing each event individually does not provide an efficient way to understand activity trends over specific time intervals.

Solution Approach

"This project builds a streaming metrics aggregation layer that receives library events through a cloud message broker, groups them into tumbling and sliding windows, and calculates real-time metrics. The aggregated results are stored in Redis and made available through a FastAPI service for visualization on a monitoring dashboard, enabling the system to track library activity and analyze event patterns over time."

7. Windowing and Aggregation Strategy

Tumbling vs Sliding time intervals and calculated metrics

Tumbling Window

A tumbling window divides the event stream into fixed, non-overlapping time intervals. Each event belongs to only one window.

Example: For a 1-minute window, the system calculates the total number of book issues and returns during each distinct minute.

Sliding Window

A sliding window calculates metrics over a fixed time interval at regular intervals. The windows overlap, allowing the system to provide frequently updated metrics.

Example: The system calculates book activity over the previous 1 minute and refreshes the results every 10 seconds.

Aggregation Metrics Calculated

Count Total number of events in window
Sum Total of applicable numeric values
Average Mean of applicable numeric values
Minimum Lowest numeric value observed
Maximum Highest numeric value observed

* Note: For events without a meaningful numeric measurement, such as BOOK_ISSUED or BOOK_RETURNED, the system counts events by type instead of calculating sum, average, min, or max.

8. Failure Handling & Recovery Matrix

Fault modes, recovery strategies, and verification test scenarios

Message Broker Failure

Broker (CloudAMQP / Kinesis) becomes temporarily unavailable.

  • Automatic reconnection with retry delays.
  • Retain unprocessed events according to broker retention.
  • Resume consumption on connection restore.

Stream Processor Failure

Python processor crashes due to unhandled exceptions or memory.

  • Exception handling & structured error logging.
  • Restart processor & save processing checkpoints.
  • Replay retained events to recover missed processing.

Duplicate Event Processing

Events processed more than once during broker retries or restarts.

  • Assign unique event ID to each library event.
  • Track processed IDs to identify duplicates.
  • Enforce idempotent aggregation logic.

Redis Storage Failure

Redis unavailable or loses in-memory data during restart.

  • Retry Redis connections and failed write calls.
  • Configure Redis persistence (RDB/AOF).
  • Rebuild window stats from retained stream events.

Failure Testing Verification Matrix

Test Scenario Expected Behaviour
Stop the message broker The processor detects the failure and reconnects when the broker returns.
Stop the Python processor Processing resumes after restart, with recovery based on saved state or replay.
Make Redis unavailable Failed writes are handled, logged, and retried where appropriate.
Send duplicate events Duplicate events are detected and do not incorrectly inflate metrics.
Interrupt the network Components recover communication after connectivity is restored.
Restart during an active window Window metrics are restored or reconstructed to the extent supported by the recovery mechanism.
