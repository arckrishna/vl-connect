1. Abstract

Core executive summary & architectural premise

This report presents the design of a Cross-Cloud Service Discovery Registry for applications whose services may run in heterogeneous cloud environments such as Amazon Web Services (AWS), Google Cloud Platform (GCP), and Microsoft Azure. Since service instances can be restarted, scaled, moved, or become unavailable, maintaining their network addresses manually can lead to stale configuration and failed requests.

The proposed course-scale system uses Consul as the service registry and health-check mechanism. Service instances register details such as service name, instance ID, address, port, tags, provider metadata, and health endpoint. A client or backend can query the registry to discover available instances, while health checks help identify services that are not responding.

The initial implementation uses Docker containers on one computer to represent services associated with different cloud providers. This provides a local demonstration of the discovery workflow, illustrating cross-environment resolution without claiming full commercial cloud deployment.

Consul Catalog Core

Centralized, high-availability service registry tracking dynamic ports, IPs, and cloud metadata.

Dynamic Health Checks

Recurring automated HTTP health probes isolating failing instances from discovery pools.

Multi-Provider Labeling

Logical grouping across AWS, GCP, and Azure mock containers for unified cross-cloud routing.

2. Introduction & Problem Definition

Problem statement, challenge definition, and project objectives

Distributed applications are commonly divided into independent microservices, each responsible for a distinct function such as user management, payments, or order processing. In a multi-cloud arrangement, these services may be hosted across different cloud providers. Their network addresses and availability can change unpredictably over time due to continuous deployments, auto-scaling events, restarts, and underlying infrastructure failures.

2.0 Problem Definition

"Without a dynamic service discovery mechanism, clients must rely on hard-coded IP addresses or manually maintained configuration files. These static approaches become unmanageable as microservices scale. The design challenge is to maintain a current service directory, let clients discover healthy instances by logical name, and continuously evaluate health states to prevent routing requests to degraded targets."

2.1 Project Objectives

Metadata Registration Register service instances and maintain their identifying and network metadata.
Logical Name Discovery Discover services by logical name without requiring clients to hard-code instance addresses.
Recurring Health Probing Perform recurring health checks and expose the current health state of each registered instance.
Multi-Provider Prototype Demonstrate example services labelled AWS, GCP, and Azure through a local Docker prototype.
Unified Dashboard UI Provide a web dashboard for service inventory, discovery results, provider labels, and health status.
Fault Tolerance Verification Test registration, discovery, failure detection, recovery, and registry-unavailable behavior.

3.1 System Assumptions

The prototype assumes that Consul and the sample microservices communicate on a reachable local Docker network bridge. The Express backend connects via a configurable Consul HTTP API URL. The AWS/GCP/Azure tags represent logical provider metadata for demonstration purposes rather than multi-region VPC peerings.

Discovery Request & Service Routing Sequence
1. Discovery Query

Client sends logical service request (e.g. payment-service) to Express Backend API.

2. Consul Catalog Check

Backend queries Consul HTTP API for healthy instances matching logical name.

3. Return Healthy Endpoints

Consul filters critical targets and returns active host IPs, ports, and cloud tags.

4. Direct Service Request

Client dispatches API payload directly to the healthy microservice instance.

Service Bootstrap & Metadata Registration
Step A: Microservice Startup

Docker container initializes on AWS, GCP, or Azure and opens HTTP application port.

Step B: Register Payload

Sends JSON payload containing Service ID, Name, Port, Provider Tag, and /health URL.

Step C: Catalog Insertion

Consul Leader node replicates registration entry across followers via Raft consensus.

Automated Health Probing & Isolation
1. Recurring Probe

Consul sends HTTP GET checks every 5s to instance /health endpoints.

2. Timeout / Crash Detection

If instance crashes or fails 3 consecutive checks, status transitions to CRITICAL.

3. Catalog Exclusion

Unhealthy instance is excluded from discovery results, preventing traffic blackholing.

5. Service Registration & Discovery Design

Schema design, registration pipelines, and text-based flowcharts

Table 4.1 Logical Service Registry Model Schema

Field Purpose Example Value
service_name Logical name queried by clients. payment-service
service_id Unique ID for one instance. payment-01
address Address at which the instance can be reached. payment-service
port Port used by the application. 8002
provider Provider label or deployment metadata. GCP
health_endpoint Endpoint checked by the registry. /health
health_status Latest reported health-check state. passing / critical
tags Optional labels used for grouping or filtering. payment, gcp
5.1 Registration Procedure
  1. Start application service & expose endpoints.
  2. Register metadata with Consul catalog API.
  3. Consul stores instance record in catalog.
  4. Query catalog to verify registration state.
5.2 Health-Check Procedure
  1. Consul executes check on endpoint at interval.
  2. Passing responses keep state active.
  3. Repeated timeouts trigger critical status.
  4. Dashboard updates health state live.
5.3 Discovery & Request Procedure
  1. Client selects logical service name.
  2. Frontend calls Node.js/Express backend API.
  3. Backend queries Consul for healthy nodes.
  4. Client dispatches request to active target.

6. Consistency, Recovery & Operational Safeguards

Fault tolerance strategies and production hardening practices

The prototype distinguishes a service's registration record from its live health status. A registered service is not automatically considered healthy. The backend explicitly handles Consul HTTP timeouts and cluster disconnects rather than presenting stale historical data as live status.

Unique Instance Identification Validate registration payloads and use unique Service IDs to prevent duplicate record collisions.
Explicit Error Handling Return structured JSON errors if Consul is unreachable rather than serving false passing statuses.
API ACL Protection Restrict public exposure of Consul management endpoints and authenticate administrative operations.
Secret Management Store tokens, keys, and cloud credentials in environment variables rather than source code.
Consistent Health Mechanism Explicitly document whether Docker container health or Consul HTTP probes drive displayed states.
Restart Verification Test automatic re-registration after container restarts prior to asserting recovery capabilities.

7. Scalability & Future Architecture

Roadmap from local prototype to enterprise production scale

The course prototype establishes a functional proof-of-concept on a local system. Moving to a commercial multi-cloud environment requires scaling the Consul control plane across cloud boundaries, securing inter-service transit, and managing cross-region latencies.

WAN Federation

Deploy Consul server agents across AWS, GCP, and Azure linked via WAN gossip for multi-datacenter synchronization.

Zero-Trust mTLS

Implement Consul Service Mesh (Connect) with automatic TLS encryption and access control policy enforcement.

Global Load Balancing

Position API Gateways behind redundant load balancers with health-aware DNS routing (e.g., AWS Route53 / Cloudflare).

9. Performance Evaluation & Acceptance Criteria

Table 9. Observed acceptance criteria and performance measurement methodology

Experiment Scenario Expected Observation / Acceptance Criterion
Service Registration A registered service appears in Consul catalog with expected ID, address, port, and provider metadata.
Service Discovery A logical lookup query returns the expected matching active service instances.
Healthy Instance State A running service reports passing state according to its configured /health check.

10. Simulation & System-Level Analysis

Queueing model, component execution path, and analytical boundaries

For system-level analysis, the overall discovery and request execution path is represented as a sequential queueing model:

Client Request → Express Backend API → Consul Registry Lookup → Target Service Dispatch → Response

Simulation tests run against local Docker containers illustrate queueing behavior under varying discovery query rates. Results collected from local prototypes reflect local bridge networking and single-host scheduling rather than wide-area commercial cloud latencies.

11. Risks & Planned Mitigations

Table 11. Risk assessment matrix and mitigation strategies

Identified Risk Planned Mitigation Strategy
Provider labels mistaken for real cloud deployment Clearly document the local Docker container scope and designate multi-cloud WAN peering as future work.
Stale or unreachable service address Test network reachability from client context and ensure Consul catalog returns reachable container IPs.
Incorrect health status reporting Configure HTTP health check endpoints explicitly; test simulated failure and recovery scenarios repeatedly.
Consul service registry unavailable Implement explicit backend timeouts and display prominent error alerts in the dashboard UI.
Duplicate service registrations Enforce unique service_id generation and validate registration payloads before sending to Consul.
Unauthorized registry access Restrict local network bindings, configure ACL tokens, and protect management endpoints.
Frontend UI remains hard-coded Connect UI component state dynamically to Express backend REST API endpoints.
Overstated reliability or scalability Differentiate measured local prototype metrics from theoretical enterprise production scale.

12. Conclusion

Final engineering summary

The Cross-Cloud Service Discovery Registry project presents a complete System Design solution for managing dynamic service instances across multi-provider cloud topologies. By leveraging HashiCorp Consul, a Node.js/Express API, and containerized microservices labeled for AWS, GCP, and Azure, the system decouples client configurations from changing network endpoints.

The core end-to-end path—encompassing service registration, dynamic catalog maintenance, recurring health checks, client discovery lookups, and fault isolation—is verified through local containerized testing. The local prototype provides a practical model for learning service registry mechanics, eventual consistency, health-check probing, and fault handling in microservice architectures.
