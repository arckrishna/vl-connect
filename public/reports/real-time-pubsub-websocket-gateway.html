1. Abstract

Executive summary & core architectural premise

Mini Discord is a real-time chat backend in which thousands of users hold long-lived WebSocket connections and exchange messages across multiple channels. A single server cannot hold every connection, so users are spread across several gateway servers. A message published to a channel must still reach every subscriber, including those connected to a different gateway. Raw cloud primitives such as load balancers and managed Redis provide traffic distribution and message forwarding, but they do not understand channels, sessions, presence or heartbeats.

To address this, the project designs a Real-Time Pub/Sub WebSocket Gateway: a custom, stateful gateway layer built on top of cloud primitives. Clients connect through a Network Load Balancer (NLB) to a cluster of WebSocket gateway nodes. Each node manages connections, authentication, channel subscriptions, message routing, presence and heartbeats. A managed Redis Pub/Sub service (Redis Enterprise or Amazon ElastiCache) acts as the backplane that forwards every published message to all gateway nodes, which then deliver it to their locally connected subscribers.

Durable data is kept separately: an SQL database (Aurora / RDS) stores users, servers, channels, roles and message metadata, while S3 object storage holds avatars, attachments and media. Background workers clean stale sessions, update presence and aggregate metrics. The design targets low-latency fan-out to thousands of concurrent users, high availability and fault tolerance, and horizontal scalability using cloud primitives.

Because building and load-testing real infrastructure requires cloud accounts and cost, Phase 1 delivers the system architecture and data-flow specification together with the Distributed Systems Virtual Lab, a browser-based simulator in which the same architecture can be assembled, loaded with simulated traffic, broken with injected failures and observed through live metrics.

2. Introduction & Objectives

Problem statement and engineering objectives

Chat platforms such as Discord keep one open WebSocket connection per user. These connections are stateful: the server must remember who is connected, which channels they follow and whether they are still alive. Scaling such a system is harder than scaling a stateless web API, because a connection cannot simply be moved between servers, and a message sent on one server has to be forwarded to users who are attached to other servers.

A common approach is to run several gateway nodes and connect them through a publish/subscribe backplane. Each node publishes incoming messages to the backplane and receives every message published by the other nodes. This keeps the gateways independent of each other while still giving every subscriber a consistent real-time experience.

Cloud queues, load balancers and managed caches give delivery and elasticity, but they do not provide chat-specific behaviour. The custom gateway layer closes that gap by turning raw cloud primitives into a real-time, channel-aware chat platform. The system is organised as layers with clear responsibilities: an internet-facing load balancer, a private gateway cluster, a Redis backplane, supporting services, persistent storage and background workers.

2.1 Problem Statement

"How can a real-time chat system deliver every published message with low latency to all subscribers spread across multiple stateful WebSocket gateway nodes, while detecting dead connections, remaining available when a gateway, Redis or the database fails, and scaling horizontally as the number of concurrent users grows?"

2.2 Core Objectives

Low-Latency Delivery Deliver published messages to all subscribers across multiple gateway nodes with low latency.
Thousands of Users Support thousands of concurrent users and real-time multi-channel chat using Pub/Sub fan-out.
Authentication & Rate Limiting Authenticate clients and validate every publish request at the gateway boundary.
Liveness & Heartbeats Maintain connection liveness with heartbeats and clean up dead sessions and subscriptions.
Storage Decoupling Keep real-time delivery separate from durable storage of users, channels, message metadata and media.
Fault Tolerance Remain available and fault tolerant when a gateway node, Redis or the database fails.
Simulation Lab Provide a simulation lab that exposes throughput, latency, queues and bottlenecks, explaining why a system degrades under load.

4. Stateful Gateway & Pub/Sub Backplane Engine

Deep dive into custom gateway mechanics, connection states, and fan-out

4.1 Core Engine Overview

The Stateful WebSocket Gateway Cluster is the central custom component of the system. It is the abstraction layer built on top of the load balancer and the Redis backplane. Its main purpose is to make a group of independent gateway servers behave like one chat system: every client can connect to any node, subscribe to channels, publish messages and receive messages from users on other nodes.

1. Connection Management Accept, track, rate-limit and close WebSocket connections on each node.
2. Auth & Rate Limiting Verify JWT client tokens upon handshake and regulate publish throughput.
3. Subscription Registry Record channel interest per user and node in Redis and local memory.
4. Message Fan-Out Publish messages to Redis backplane and dispatch local socket frames.
5. Presence & Heartbeat Exchange PING/PONG heartbeats and purge stale sessions automatically.

4.2 Connection Management and Load Balancing

When a client opens a wss:// connection, the NLB routes it to a healthy gateway node. The node authenticates the client, creates a session and registers presence in Redis. The connection then stays on that node until the client disconnects or the node fails. Because the node holds the open socket, it is the only place from which that client can be reached, which is why the system needs a backplane for cross-node delivery.

The NLB distributes connections across healthy nodes (for example round-robin or least-connections) and stops sending traffic to a node once its health check detects a failure. An Auto Scaling Group adds or removes gateway nodes based on active connections. When a new gateway is added, connections are gradually rebalanced onto it, and each node enforces a per-node connection limit so that no single node is overloaded.

4.3 Channel Subscription and Subscription Registry

Channels (rooms) group users who want to receive the same messages. When a client sends SUBSCRIBE for a channel such as #general, the gateway adds a subscription record containing the userId, channelId and nodeId to the Subscription Registry in Redis and returns an ACK.

// Redis Subscription Registry Structure
HSET registry:channel:#general user:1001 "node:gw-2"
SADD node:gw-2:channels "#general"
// Local Node Memory Registry:
Map<ChannelID, Set<WebSocketConnection>>

4.4 Redis Pub/Sub Backplane and Fan-Out

The Redis Pub/Sub backplane connects the gateway nodes. When a gateway receives a valid message from a publisher, it delivers the message to its own local subscribers and publishes it to the Redis channel. Redis forwards the message to every other gateway node, and each node finds its local subscribers and pushes the message over their open WebSockets.

The origin gateway delivers to its own subscribers locally, and the broadcast skips it, so no message is delivered twice. One published message can therefore produce many deliveries: with 20 recipients per message, one publish becomes 20 deliveries spread across the gateways according to their share of connections.

4.5 Presence and Heartbeat Handling

Long-lived connections can die silently, for example when a phone loses network. To detect this, the client and the gateway exchange PING and PONG messages periodically. If no PONG is received within a timeout T, the gateway marks the connection as dead, closes it and cleans up the session and subscriptions in Redis.

4.6 Persistence & Media Storage

Persistence is kept on a separate path from real-time delivery. After validation, message metadata is written asynchronously through a background worker to the SQL database (Aurora/RDS). Large media files are uploaded through the Media Service to S3 object storage, keeping chat frames small.

4.7 Scalability & Fault Tolerance

The gateway cluster scales horizontally by adding nodes as connection count rises. NLB health checks remove failed nodes within 3 seconds, forcing clients to reconnect to surviving nodes while heartbeats clean up dead state in Redis.

5. Data Flow, Security & Failure Handling

Data store roles, edge-case failure matrix, and security guardrails

5.4 Data Stores & Roles Summary

Data Store Role & Responsibilities
Redis (Pub/Sub + State) Pub/Sub channels for message fan-out; session store (userId to nodeId, expiry); subscription registry (channel to set of nodes and users); presence and heartbeats.
SQL Database (Aurora / RDS) Users, servers, channels, roles; message metadata (message id, channel id, sender id, timestamp); attachment and link metadata.
S3 Object Storage Avatars, attachments, media files and generated thumbnails. Large files are uploaded to S3 and only links and metadata are shared in messages.

5.5 Failure and Edge Case Strategy

Failure / Edge Case Behaviour & Detection Recovery Strategy
Gateway crash Node shows DOWN with 0 connections. NLB detects health check failure within 3s. Clients reconnect to surviving gateways within connection limit; recovered node slowly regains load.
Redis outage Local delivery continues but cross-gateway events are lost; delivery ratio drops. Events are not replayed on recovery unless gateway buffer is enabled to re-send late events.
Database outage Persistence writes fail out-of-band; reported separately from delivery errors. Real-time chat continues unaffected; async worker queue absorbs writes until DB recovers.
Traffic spike / overload Gateways reach 100% busy, queues fill, P99 latency climbs and errors rise. Throughput plateaus at capacity; Auto Scaling Group provisions additional gateway nodes.
Slow consumer / queue overflow Subscriber or node queue cannot keep up with high fan-out rate. Finite FIFO queues, drop timeouts and optional backpressure prevent unbounded memory leaks.
Reconnect storm Many clients reconnect simultaneously following network flappers or node reboot. Per-node connection limits and NLB round-robin spread clients across healthy fleet.
Dead connection No PONG received within timeout T. Socket force-closed; background worker cleans session & subscriptions in Redis.
Duplicate delivery to origin Origin gateway receives its own broadcast back from Redis. Origin delivers locally first and skips the Redis echo to avoid double delivery.

5.6 Security Considerations

Only the Network Load Balancer is internet-facing; all gateways, Redis, databases, and workers reside in private VPC subnets. Auth Service validates JWT/OAuth2 tokens before socket admission. Redis rate-limit counters restrict abusive clients, and media attachments pass through S3 pre-signed URLs.

6. Simulation & Verification

Phase 1 Virtual Lab engine benchmarks and scenario test results

The Phase 1 implementation is the Distributed Systems Virtual Lab, a single-page web application with a strict boundary between the user interface and the simulation logic. A framework-free TypeScript simulation engine runs in fixed 100 ms steps, moves batches of work with fractional counts (a fluid model) through finite FIFO queues, and records offered, accepted, completed, delivered and dropped throughput, utilisation and P50 / P95 / P99 latency.

Scenario Setting Observed Result (Seed 42 Defaults)
Healthy baseline 100 msg/s offered Completed ~100/s; deliveries ~2,000/s; delivery ratio 100%; errors 0%; P50 ~73 ms; P99 ~78 ms; each GW ~36% busy with 200 conns.
Overload 600 msg/s offered Gateways 100% busy; completed throughput plateaus near 390/s; errors ~35%; P99 ~2 s; Gateway named bottleneck.
Redis outage Down at t=10s for 15s Completed stays ~100/s; deliveries fall to ~667/s; delivery ratio ~33%; errors ~65%.
Redis outage + buffer Same outage, buffer ON Errors stay near 0%; gateways hold events and re-send them late after recovery.
One gateway crash GW-1 down at t=10s for 25s 200 clients reconnect to GW-2 and GW-3 after 3s NLB health-check delay; health degraded then recovers.

9. Conclusion

Final engineering summary

The Real-Time Pub/Sub WebSocket Gateway shows how a thin custom layer of stateful gateway nodes, a Redis Pub/Sub backplane and a load balancer can deliver real-time, multi-channel chat to many concurrent users. Connections stay on the node that accepted them, Redis fans each message out to all gateways, and the SQL database keeps history separately because Pub/Sub is transient.

The key contribution of the project is establishing a channel-aware gateway layer between raw cloud primitives and users, where subscriptions, presence and heartbeats govern how messages are routed and how failures are handled. The Virtual Lab makes this behaviour visible: the system saturates predictably under overload, local delivery survives a Redis outage, and a gateway crash is absorbed by reconnecting clients to the surviving nodes.
