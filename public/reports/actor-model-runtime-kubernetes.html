1. Abstract & Abbreviations

Executive summary, design targets, and core terms

ActorLab turns a managed Kubernetes cluster and a PostgreSQL database into a virtual actor runtime. Kubernetes supplies disposable pods, replica scaling and restarts; PostgreSQL supplies durable, strongly consistent storage. The custom layer built on top of them gives every logical actor a stable identity, a private mailbox, durable state and exactly one valid owner at any moment, no matter which pod hosts it. A control plane routes each message to the actor's owner, runtime pods process each actor's mailbox sequentially, and ownership is held as a lease with a monotonically increasing epoch (fencing token) in the database. When capacity changes, a rebalancer moves only the actors that must move, using a drain, flush and fenced handover. Singleton actors use database leases with fencing tokens.

The design targets four guarantees: linearizable per-actor state through single-owner, version-checked writes; fault tolerance for pod and control-plane crashes with state preserved; at-least-once delivery with idempotent deduplication, giving effectively-once state effects; and safe rebalancing and singleton ownership through fencing. This is a Phase 1 System Software Design report. It specifies requirements, architecture, data model, state machines, pathways, failure handling, security and a validation plan.

Keywords: virtual actors, actor model, Kubernetes, horizontal pod autoscaler, fencing token, lease, epoch, idempotency, rendezvous hashing, rebalancing, singleton, fault tolerance.

2. Introduction & Objectives

Background, problem statement, and 8 core objectives

Kubernetes schedules containers, restarts failed pods and adjusts replica counts, but it has no concept of a logical actor. A pod is disposable: when it dies, everything in its memory is gone. A Kubernetes Service load-balances each request to any ready pod, so two requests for the same logical entity can reach different pods and race on the same state. Kubernetes cannot guarantee that one entity has one owner, cannot move an entity's state when replicas are added or removed, and cannot tell a replacement pod from a recovered entity. Typical uses that need these properties are per-user or per-device state, counters and sessions, stateful workers, and coordinators that must run exactly once.

1.2 Problem Statement

"How can disposable, interchangeable pods and a database be turned into a runtime in which every logical actor has one valid owner, durable state and ordered message processing, that rebalances safely when capacity changes and recovers from pod and control-plane failures without losing or double-applying work?"

1.3 Project Objectives (01 to 08)

01 Give each logical actor a stable identity independent of the hosting pod.
02 Process each actor's messages sequentially in mailbox order, and different actors concurrently.
03 Persist actor state durably and recover it after pod replacement.
04 Guarantee a single valid owner per actor using epoch-based fencing.
05 Rebalance actors safely when replica counts change (drain, flush, fenced handover).
06 Provide singleton actors with one valid owner using leases and fencing tokens.
07 Achieve effectively-once state effects on top of at-least-once delivery using message-ID deduplication.
08 Scale runtime on Kubernetes (manual/HPA), report observed state honestly, and show real metrics.

Core Algorithms Pseudocode (A to E)

// Algorithm A: Router Submitting Message
function submit(actor_id, message):
  row = SELECT owner_runtime_id, epoch, status FROM actors WHERE actor_id
  if row.owner is null or row.status in (DEACTIVATED, ORPHANED):
    row = placement.activate(actor_id)
  if row.status == MIGRATING: return buffer(actor_id, message)
  for attempt in 1..MAX_ROUTE_ATTEMPTS:
    reply = POST owner_pod/actors/{actor_id}/messages {message, epoch}
    if reply.ok: return reply
    if reply is 409 NOT_OWNER: sleep(backoff(attempt)); re-read ownership
  return 503 RETRYABLE
// Algorithm B: Runtime Fenced Transaction Commit
actor loop (sequential mailbox):
  m = mailbox.dequeue()
  BEGIN TRANSACTION
    SELECT 1 FROM actors WHERE actor_id AND owner_runtime_id = me AND epoch = my_epoch FOR SHARE
    if no row: ROLLBACK; stop hosting actor (STALE_OWNER); return 409
    (new_state, result) = behavior.handle(state, m)
    UPDATE actor_states SET state = new_state, version = version + 1 WHERE actor_id AND version = v
    if updated == 0: ROLLBACK; reload state; retry
    UPDATE messages SET status = 'DONE', result = result WHERE message_id
  COMMIT

Client → Gateway → Control Plane → PostgreSQL Primary Read (Committed state & version). Pods and mailboxes are never touched for reads.

Reconciler Loop | Scaling Loop | Metrics Loop | Lease Heartbeat Loop | Rebalancer Worker | In-flight Message Recovery Worker.

Figure 8: Manual vs Automatic Scaling

User set desired replicas vs Workload Generator CPU spikes → metrics-server → HPA patch Deployment → Reconciler pod Ready check.

Figure 9: Safe Actor Migration Protocol (Fenced Handover)
  1. Mark MIGRATING: Router buffers incoming new messages for the actor.
  2. Drain: Old owner finishes current message execution and accepts no more.
  3. Flush: Old owner commits final state (version v) to PostgreSQL.
  4. Handover Transaction: Single SQL TX sets new owner, epoch + 1, and records COMPLETED migration. Old owner is immediately fenced.
  5. Activate: New owner loads state version v and becomes ACTIVE. Router flushes buffered messages.

9. Consistency & Correctness

Invariants I1 to I9 and correctness guarantees

Invariants Preserved (I1 to I9)

I1. Single Owner Only runtime named in actors row with matching epoch can commit.
I2. Monotonic Epoch Epoch increases on every owner change and never decreases.
I3. Versioned State State commit increments version by 1 guarded by version + epoch.
I4. Idempotency Message has at most one effective DONE transition (unique ID).
I5. Persisted ACK Asynchronous messages persisted as RECEIVED before ACK.
I6. Active Only An actor that is not ACTIVE processes no messages.

10. Failure Strategy & Singleton Fencing

Figures 10 & 11 — Pod restart vs State recovery & Fencing tokens

Figure 10: Pod Restart vs ActorLab State Recovery

Kubernetes responsibility replaces the pod (ReplicaSet -> Readiness probe). ActorLab responsibility detects missed lease heartbeats, marks actors ORPHANED, reassigns them with epoch + 1, reloads state from PostgreSQL, and verifies unfinished messages. A pod restart is NOT reported as an actor recovery until verified.

Figure 11: Singleton Failover & Fencing Tokens

Singleton Coordinator acquires lease with fencing token (e.g., token 11). If Runtime A stalls or experiences GC pause, lease expires. Runtime B acquires lease with token 12. When Runtime A wakes up and attempts a write with token 11, PostgreSQL REJECTS it (11 < 12).

15. Conclusion & Future Scope

Final engineering summary and Phase 2 roadmap

ActorLab adds a thin but carefully specified layer, ownership epochs and fenced commits over disposable pods and a database, that supplies what Kubernetes lacks: stable actor identity, ordered processing, durable state, safe rebalancing and exclusive singletons.

1. KEDA Queue Autoscaling Scale pods based on mailbox backlog metrics rather than CPU.
2. Database Sharding Shard PostgreSQL by lab_id or actor_id to scale write throughput.
3. TLA+ Formal Verification Formal model of epoch fencing and handover safety rules.
