1. Abstract

Executive summary of the coordination service

Distributed applications frequently require one active process to coordinate access to a shared resource. A local mutex cannot protect a resource across multiple machines, and a simple database flag can become unsafe when the lock holder pauses, the coordinator crashes, or the network is partitioned. This report proposes a fault tolerant distributed lock service that exposes named locks through a stable client API and maintains authoritative ownership using a three node replicated coordinator cluster.

The design runs on cloud virtual machines inside a private virtual network. A leader orders lock mutations and replicates them through a Raft style consensus protocol. A mutation becomes successful only after a two of three quorum durably acknowledges it. Time bounded leases recover abandoned locks, while monotonically increasing fencing tokens allow the protected resource to reject delayed operations from an earlier owner. Write ahead logs and snapshots preserve committed state during node restart.

The architecture deliberately favors consistency over write availability when a quorum is unavailable. It defines acquisition, renewal, release, query and watch operations; identifies the client, consensus, persistence and observability paths; and specifies recovery behavior for coordinator crashes, client failures, network partitions, duplicate requests and storage corruption. The resulting Phase 1 design provides a clear implementation and validation blueprint for Phase 2.

2. Introduction

System context and synchronization challenges

Modern systems divide work across many application instances so that they can scale and survive failures. This distribution creates situations in which several processes may attempt the same critical activity at the same time. Examples include running a scheduled job, updating scarce inventory, performing a payment settlement, electing a service leader, applying a schema migration or writing to a shared file. Without coordination, duplicate execution can corrupt data or cause an external side effect more than once.

A distributed lock service provides a common coordination point. A client requests ownership of a named resource, uses the resource while the ownership is valid and then releases or renews it. Unlike a local synchronization primitive, the service must remain correct when messages are delayed, clients stop without releasing, coordinator nodes restart or parts of the network cannot communicate.

The assigned case study requires a system design abstraction above a cloud VM cluster and VPC. The proposed design converts those raw primitives into a Chubby or etcd style coordinator. The VMs supply computation, the VPC provides network isolation and persistent durable block volumes retain logs, but the safety guarantee comes from consensus, replicated state, lease rules and fencing enforcement.

2.1 Distributed Lock in Simple Terms

Imagine several workers sharing one key to a protected room. The coordinator gives the key to one worker for a limited period. Every new key carries a larger serial number. Even if an old worker returns late, the room accepts only the latest serial number, so the old key cannot perform a new action.

2.2 Why a Basic Lock Flag Is Insufficient

  • The owner may crash without clearing the flag, leaving the resource permanently blocked.
  • Two coordinator replicas may independently grant ownership during a network partition.
  • A delayed client may continue writing after its ownership has expired.
  • A retry after a lost response may create a second lease unless requests are idempotent.
  • An in-memory lock table disappears when the coordinator restarts.

3. Problem Statement and Objectives

Problem scope and design objectives

3.1 Problem Statement

How can a cloud hosted service coordinate exclusive access to named shared resources while remaining safe during concurrent requests, coordinator failures, network partitions, client pauses and restart recovery? The system must ensure that two clients cannot both perform valid protected operations for the same lock, while continuing service after any one coordinator node fails.

3.2 Objectives

Provide acquire, renew, release, get and watch operations through a simple client API.
Maintain one authoritative, ordered lock state across three coordinator nodes.
Commit mutations only after a majority quorum acknowledges the same log entry.
Issue strictly increasing fencing tokens for every successful ownership grant.

3.3 Scope

Included in Initial Design Outside Initial Scope

4. Requirements and Design Decisions

Functional and non-functional requirements & CAP decision

4.1 Functional Requirements

FR1: A client can acquire a free named lock and receive a lease identifier and fencing token.
FR2: A current owner can renew its lease before expiry.
FR3: A current owner can release its lease before expiry.
FR4: A client can query current committed lock metadata.
FR5: A client can watch ordered lock state changes from a committed revision.

4.3 Consistency and CAP Decision

The service is designed as a CP system during a partition. It preserves consistency and partition tolerance and may reject or delay writes when the caller cannot reach a quorum-capable leader. Read operations claiming linearizability must also be confirmed by the leader and quorum; explicitly stale diagnostic reads may be served by a follower and labelled accordingly.

5. System Architecture

Figure 1 Architecture Flowchart and Component Responsibilities

Clients call one stable endpoint through a health-aware load balancer and API gateway. The gateway handles transport security, authentication and rate limiting, while a leader routing layer forwards mutations to the elected leader. Inside the private VPC, three coordinator nodes replicate the ordered command log. Every node owns a persistent durable block volume containing its WAL and snapshot. A separate protected resource validates fencing tokens before accepting side effects.

6. Core Distributed Lock Engine

Consensus, Quorum, Leases, Fencing Tokens, and Persistence

6.1 Consensus and Quorum

The three coordinators form a replicated state machine. One node is the leader for a numbered term. Followers accept log entries from that leader and reject stale terms. For a three-node cluster, quorum equals two. The leader commits an entry only after it and at least one follower have durably recorded the entry.

6.2 Leases

Every grant has a bounded time to live. The owner renews before expiry. If renewals stop, the leader proposes an expiry command. Followers do not independently expire and regrant locks based on their local clocks.

6.3 Fencing Tokens

Each successful acquisition increments a persistent token counter. A client includes its token with every protected operation. The downstream resource remembers the highest token it has accepted and rejects any older token, closing the paused client problem.

6.4 Persistence and Recovery

Before acknowledging replication, a node appends the entry to its write-ahead log (WAL) and performs a durable flush onto durable block storage. Periodic snapshots capture state machine revisions.

7. Data and Control Pathways

Write, renewal, release, read, and background control pathways

7.1 Lock Acquisition Write Path

  1. Client SDK sends Acquire with lock name, client identity, TTL, and request ID.
  2. Gateway authenticates request and routes to reachable coordinator.
  3. Follower forwards mutation to current leader or returns leader hint.
  4. Leader checks committed state, allocates next fencing token, and appends grant command.
  5. Leader replicates command to followers and waits for majority quorum commitment.
  6. State machine applies grant and returns lease ID, token, expiry, and revision.

7.4 Background Control Path

Worker Trigger Action
Lease Reaper Leader timer Proposes expiry commands for overdue leases.

9. Failure and Recovery Strategy

Fault tolerance matrix and restart recovery sequence

Failure / Edge Case Expected Behavior Safety Outcome
Leader Crash Followers miss heartbeats and elect new leader. Committed grants survive; clients retry.
Quorum Loss Authoritative writes fail or time out closed. Safety preserved while availability pauses.
Paused Stale Client Downstream write carries older token. Protected resource rejects operation.

10. Deployment Network and Security

VPC deployment, network rules, and security controls

Three Linux coordinator VMs placed in one VPC across three availability zones, with one durable block volume per VM. Mutual TLS secures peer communication, while consensus and storage ports remain strictly private.

11

11. Capacity Performance and Availability

Capacity sizing, latency path, and availability model

Designed for 200,000 daily operations (~2.3 ops/sec average, ~23 ops/sec peak prototype). Single-region p95 acquire latency target is below 200 ms. A three-node cluster tolerates 1 node failure with 2/3 quorum.

14. Advantages, Limitations and Future Scope

Architectural strengths and future roadmap

Advantages: Reusable coordination service, split-brain prevention via majority quorum, lease recovery, and fencing token protection.

Limitations: Single-region initial cluster, write availability stops during quorum loss, and fencing requires client cooperation.

15

15. Conclusion

Final engineering summary

The proposed Fault Tolerant Distributed Lock Service transforms a cloud VM cluster, private networking, and durable block storage into a specialized coordination abstraction. The most important design decision is to fail closed when authoritative state is uncertain, ensuring data safety above all else.
