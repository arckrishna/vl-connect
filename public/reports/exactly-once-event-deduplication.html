Abstract

Executive summary of the de-duplication engine

Distributed event pipelines usually guarantee at-least-once delivery, which means the same event can reach a consumer more than once. This report describes a de-duplication engine that gives the pipeline an exactly-once effect: every event changes downstream state once, even when it is delivered several times. It covers the architecture, the processing flow, the main failure modes and their mitigations, and a self-contained browser simulation built to teach the concept. The simulation runs as a single static page with no backend.

01

1. Problem statement

Why at-least-once delivery causes duplicate execution hazards

Messaging systems favor at-least-once delivery because it never loses data. The cost is duplicates, and they come from several places:

  • Producers retry when an acknowledgement is lost, even though the first send succeeded.
  • Brokers redeliver messages after a consumer crash or a partition rebalance.
  • Networks can repeat a packet or a request.

Duplicates are harmful when the effect is not naturally repeatable: charging a card twice, sending a notification twice, or counting a metric twice. The engine therefore has to detect repeats and make sure the effect happens once.

02

2. Design goals and guarantee

Correctness, bounded state, scalability, and containment

Guarantee. The engine provides exactly-once effect, not exactly-once delivery. Events may be delivered many times, but the observable result is the same as if each had been processed once. This is achieved by combining at-least-once delivery with idempotent processing.

Correctness No duplicate effects, even across crashes and retries.
Bounded State The set of seen IDs must not grow forever, so entries expire after a TTL.
Scalability The de-duplication tier scales horizontally by partitioning on the event ID.
Containment Slow components must not cause an unbounded retry storm.

3. Architecture

Figure 1 Architecture Diagram and Component Responsibilities

The system has four tiers: ingest, de-duplication, effect, and a failure path. Figure 1 shows the components and how events move between them.

Figure 1 — Architecture of the de-duplication engine
1. INGEST TIER
• Producers (Stable ID)
• API Gateway (Auth/Rate limit)
• Event stream (Keyed partitions)
2. DEDUP TIER
• Local ID cache (Hot IDs in memory)

3. EFFECT TIER
• Record event ID (Unique ID insert)
• Apply effect (Idempotent write)
• Downstream sink (Sees each once)
4. FAILURE PATH
• Retry queue (Backoff, re-enter)
• Dead letter queue (Held for replay)
Re-enters dedup tier on retry

3.1 Components

Component Role Key Design Choice
Producers Emit events with a stable, producer-assigned event ID and retry when an acknowledgement is missing. The ID must be identical on every retry. Otherwise a duplicate cannot be told apart from a new event.
API gateway Authentication, rate limiting and request validation. Shields the stream from bursts and rejects malformed events before they cost a lookup.
Event stream Durable, partitioned log that decouples producers from workers. Partitioned by event key so every copy of an event reaches the same worker.
Dedup workers Stateless pool that checks each event ID, drops repeats and forwards new events. Stateless, so they scale horizontally. Their capacity is the throughput ceiling of the dedup tier.
Local ID cache In-memory cache of recently seen IDs. Absorbs the common case of immediate duplicates without a network round trip.
ID store Sharded store of seen event IDs with a time-to-live (TTL). Sharding by hash of the event ID spreads load. The TTL bounds memory on high-performance durable block storage / NVMe.
Effect transaction Inserts the event ID under a unique constraint and applies the effect in one atomic transaction. Closes the gap where a crash between processing and recording would allow a second execution.
Downstream sink Consumes the processed events. Sees the effect of each event once.
Retry queue Redelivers events whose write timed out. Exponential backoff with jitter prevents synchronized retries.
Dead letter queue Holds events that exhausted their retries. Preserves events for inspection and replay instead of silently dropping them.

4. Processing flow

Step-by-step lifecycle of an event through the pipeline

  1. A producer assigns a stable event ID and sends the event through the API gateway.
  2. The gateway authenticates and rate-limits, then appends the event to the partitioned stream, keyed so that all copies of an event land on the same partition.
  3. A de-dup worker reads the event and checks the local ID cache, then the sharded ID store.
  4. If the ID has been seen, the worker drops the event. This is the duplicate-blocked path.
  5. If the ID is new, the worker forwards it to the effect tier.
  6. The effect tier inserts the ID under a unique constraint and applies the effect in a single atomic transaction. Either both happen or neither does.
  7. If the write times out, the event goes to the retry queue with backoff and re-enters the dedup tier. After the maximum attempts it moves to the dead letter queue.

5. Failure modes and mitigations

Handling broker duplicates, retries, crashes, contention, and retry storms

Failure Mitigation Notes
Duplicate delivery by the broker or network The ID lookup finds the event already seen and drops the copy. Handled in the local cache or the ID store.
Producer retries after a lost acknowledgement The retry carries the same event ID, so it is treated as a duplicate. Requires producer-assigned IDs that are stable across retries.
Crash between processing and recording the ID Record the ID and apply the effect in one atomic transaction. With check-then-record as separate steps, the retry applies the effect twice.
Lock contention on the processed-events store Monitor lock wait, shard hot keys, and apply backpressure upstream. Slow writes time out and trigger retries, which add more load.
Retry storm Backoff with jitter, a retry budget, and a maximum attempt count before the dead letter queue. Immediate unbounded retries consume the worker capacity that fresh events need.
Late duplicate after the TTL expires Set the TTL longer than the longest retry window. Keep a unique constraint on the durable store as a backstop. A duplicate that outlives the TTL looks like a new event.
Poison event that always fails After the maximum attempts, move it to the dead letter queue for inspection and replay. Stops one bad event from blocking the pipeline.

7. Deployment

Hosting as a single self-contained index.html file

The simulation is one self-contained index.html file. It uses no libraries, no network requests, and no external fonts, so it can be served by any static host. The options considered were GitHub Pages, Cloudflare Pages, Netlify, Vercel and Render. GitHub Pages was chosen for the walkthrough: create a public repository, upload index.html at the root, and enable Pages from the main branch. Once published, the page runs on the host and does not depend on the author's computer.

For GitHub Pages, the documented limits are a published site of 1 GB or less and a soft bandwidth limit of 100 GB per month. Limits can change, so they should be checked before relying on a host.

8. Future work

Roadmap for extended simulation and production engine features

Track individual event IDs so the learner can follow one event through the pipeline.
Model TTL expiry and show a late duplicate slipping past the ID store.
Add backoff with jitter as a control and compare it with immediate retries.
Add dead letter queue replay and a configurable retry budget.
09

9. Conclusion

Final engineering summary

Exactly-once effect comes from two pieces working together: a de-duplication tier that drops repeats cheaply, and an atomic, idempotent write that makes retries safe. The failure analysis and the simulation show the same point from two angles. De-duplication alone is not enough when the store is slow, because retries then become the main source of load and of duplicate effects.
