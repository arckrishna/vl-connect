1. Abstract

Core executive summary & system goals

LegalVault is a secure document management system designed for lawyers and law firms to manage legal cases, notes, documents, images, and videos. Legal information is highly confidential, and unauthorized access or data leakage can have serious consequences. Traditional storage systems often depend on application-level access controls, which may not provide sufficient protection if stored data is exposed.

To address this problem, LegalVault introduces a Multi-Tenant Encrypted Database Proxy Engine, implemented as an independent cryptographic microservice called Crypto-Proxy. It acts as a security layer between application services and storage systems. Its primary responsibility is to encrypt and decrypt sensitive information, manage tenant-specific encryption keys, and enforce tenant isolation.

The system uses a Next.js frontend, separate authentication, case and file services, MongoDB for structured case data, and Backblaze B2 for file storage through an S3-compatible interface. The authentication service uses RS256-signed JSON Web Tokens (JWTs), while the Crypto-Proxy uses AES-256-GCM encryption to protect stored information.

The main objective is to ensure that application services do not directly handle encryption keys or store sensitive information in plaintext. Each tenant has a separate encryption context, reducing the risk of unauthorized cross-tenant access. The architecture also incorporates key versioning and rotation to support long-term data protection.

Strict Tenant Isolation

Cryptographically separated contexts preventing cross-firm data leaks.

AES-256-GCM Protection

Authenticated encryption ensuring both confidentiality and data integrity.

Zero Plaintext Storage

Application services and storage drivers never retain unencrypted keys or files.

2. Introduction & Objectives

Context, security motivation, and platform goals

Lawyers handle confidential information such as client details, case records, contracts, evidence, legal notes, scanned documents, images, and recordings. Storing this information digitally improves accessibility and organization, but it also introduces security risks.

In a multi-tenant application, multiple law firms use the same platform. Although they share the application infrastructure, their information must remain strictly separated. A security failure that allows one firm to access another firm's records can compromise client confidentiality.

Traditional applications often implement encryption separately within individual services. This approach can result in duplicated encryption logic, inconsistent security practices, and unnecessary exposure of encryption keys across the application.

LegalVault addresses these challenges through a microservices architecture in which authentication, case management, file handling, and cryptographic operations are separated.

The central component is the Multi-Tenant Encrypted Database Proxy Engine. Instead of allowing the case and file services to access protected storage directly, LegalVault routes sensitive storage operations through the Crypto-Proxy. The proxy determines the tenant identity from a verified JWT, selects the appropriate encryption key, performs the required cryptographic operation, and communicates with the storage system.

"How can a multi-tenant legal document management system securely store confidential case information and files while preventing unauthorized access between tenants, minimizing exposure of encryption keys, and supporting controlled key rotation?"

4. Multi-Tenant Encrypted Database Proxy Engine

Detailed security component architecture & cryptographic specifications

4.1 Proxy Engine Overview

The Multi-Tenant Encrypted Database Proxy Engine is the central security component of LegalVault. It is implemented as an independent microservice that sits between application services and storage systems. Its main purpose is to ensure that sensitive information is encrypted before being stored and decrypted only when an authorized request requires it.

Without this proxy, the case service and file service would need to implement encryption independently and manage access to encryption keys. This would increase code duplication and create additional opportunities for security errors.

1. Tenant Isolation Separate encryption contexts for different law firms.
2. Key Management Create, retrieve, rotate, version, and revoke tenant keys.
3. Data Encryption Protect structured database records and uploaded files.
4. Storage Mediation Control access to MongoDB and S3-compatible Backblaze B2.
5. Request Auth Verify RS256 JWTs before enabling cryptographic operations.

4.2 Multi-Tenant Key Management

Multi-tenancy allows multiple law firms to use one application without sharing their confidential information. LegalVault enforces this separation through tenant-specific encryption keys.

Tenant A → Key A Tenant B → Key B Tenant C → Key C

When a request arrives, the Crypto-Proxy verifies the JWT and extracts the tenant ID from the verified token. It then selects the key associated with that tenant. The tenant ID supplied in a request body or URL is not sufficient by itself to establish authorization. The proxy must use the verified identity and confirm that the requested record or file belongs to the same tenant. If Tenant A attempts to access Tenant B's data, the proxy rejects the operation rather than using Tenant B's key.

4.3 AES-256-GCM Encryption and Decryption

LegalVault uses AES-256-GCM to encrypt sensitive information. AES is a symmetric encryption algorithm, meaning the same secret key is used for encryption and decryption. Galois/Counter Mode (GCM) additionally provides authentication, helping detect unauthorized modification of encrypted data.

// Conceptual Cryptographic Pipeline
Plaintext → Tenant Key Selection → Unique Nonce + AES-256-GCM → Ciphertext + Auth Tag → Storage

For secure operation, each encryption must use a unique nonce with a given AES-GCM key. The nonce, authentication tag, ciphertext, and required key-version metadata are stored together. Secret encryption keys are never stored alongside plaintext data.

4.4 Envelope Encryption Architecture

LegalVault's design includes envelope encryption to improve key management as the amount of stored data increases. Instead of encrypting every file directly with a long-lived master key, a unique Data Encryption Key (DEK) is generated for an individual file or record. That DEK encrypts the actual content, while a Key Encryption Key (KEK / Tenant Master Key) encrypts the DEK.

1. Generate DEK
2. Encrypt Payload with DEK
3. Encrypt DEK with KEK
4. Store Encrypted DEK + Data

4.5 Key Versioning and Rotation

Encryption keys should not remain unchanged forever. Every encrypted record or file identifies the key version used to encrypt it (e.g., Tenant A Key v1). During rotation, new writes use the latest key version (v2), while existing records remain decryptable using v1 until re-encrypted or migrated.

4.6 MongoDB & Backblaze B2 Proxy

The proxy mediates MongoDB case storage and Backblaze B2 file uploads. S3 object paths enforce tenant namespace separation:

tenantId/caseId/fileId

5. Authentication, Security & Data Flow

RS256 token verification, write/read sequences, and security boundary matrix

5.1 RS256 JWT Auth

Auth service signs JWTs via RS256 private key. Crypto-Proxy validates tokens independently using the public JWKS endpoint.

5.2 Case Data Flow

Frontend routes request to Case Service with JWT. Proxy verifies token, derives tenant context, encrypts record, and writes to MongoDB.

5.3 File Handling Flow

File Service checks metadata/size and delegates binary stream encryption to Crypto-Proxy before pushing ciphertext to Backblaze B2.

5.4 Security Safeguards Summary

• Tenant Key Segregation Eliminates cross-tenant data exposure vectors.
• Centralized Crypto Scope Eliminates duplicated microservice encryption logic.
• RS256 JWT Verification Rejects unauthenticated or tampered storage calls.
• AES-256-GCM Integrity Prevents silent ciphertext tampering via auth tags.

8. Conclusion

Summary & system takeaway

LegalVault demonstrates a microservices-based approach to secure legal document management, with the Multi-Tenant Encrypted Database Proxy Engine serving as its primary security component.

The Crypto-Proxy centralizes encryption, decryption, tenant-specific key selection, key versioning, and storage access for MongoDB and Backblaze B2. By separating authentication, business logic, and cryptographic operations, the system reduces the need for individual application services to handle encryption keys directly.

The combination of RS256-based JWT verification, AES-256-GCM encryption, tenant-specific keys, and controlled storage access provides a foundation for protecting confidential legal information in a multi-tenant environment.

The key contribution of LegalVault is not simply encrypting files or database records. It is establishing a dedicated cryptographic boundary between application services and storage, where tenant identity and key selection govern access to protected information.
