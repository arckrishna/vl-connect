1. Abstract

Core executive summary & architectural premise

Feature flags let teams release, test and switch off features without deploying new code. At high traffic, a design in which every flag check is a remote call to a central service becomes slow, fragile and expensive. This project presents an interactive virtual lab and simulator for a low-latency distributed feature flag service that avoids these problems.

The system separates two paths. On the hot evaluation path, a Client SDK evaluates flags from an in-memory cache and needs no network call, giving a modelled evaluation time of about 1.3 ms. On the cold control-plane path, an admin change is stored in cloud storage, published through a Pub/Sub broker and pushed to the clients through Server-Sent Events (SSE), which takes a modelled 32.5 ms under normal conditions.

The lab models 10 architectural components and represents simulated utilization, latency, throughput and dropped requests. It includes an interactive architecture canvas, ShopEasy preview, charts, fault injection and an event log. Performance values are generated by the model rather than measured on hardware.

Hot Evaluation Path

Evaluates flags locally in-memory via SDK cache with ~1.3 ms latency without remote database lookups.

Cold Control Plane

Pushes admin flag changes through Pub/Sub and SSE in ~32.5 ms background window.

ShopEasy Preview

Interactive mobile preview toggling between standard card checkout and 1-Click Express payment.

2. Introduction & Objectives

Problem statement, goals, and target scope

Feature flags (feature toggles) are used by large applications such as e-commerce sites, streaming services and social networks. They support continuous delivery, gradual rollouts (canary releases), A/B experiments and emergency kill switches. A busy application may check flags thousands of times every second, so the way flags are evaluated affects both speed and reliability. Production systems such as LaunchDarkly and Split.io evaluate flags locally inside an SDK and send updates to the clients in the background. This project builds a virtual lab that explains and demonstrates this design.

2.1 Problem Statement

"A naive design makes a remote HTTP or RPC call to a central flag service or database for every flag evaluation. This creates severe latency overhead (20-150 ms), introduces single points of failure, and causes database exhaustion at 50,000 req/s. The problem is to design a feature flag service in which evaluation is fast and keeps working during backend failures, while admin changes still reach all clients."

2.2 System Objectives

Path Decoupling Show that the hot evaluation path is separate from the cold configuration-update path.
10-Component Model Model 10 components and show how simulated utilization, throughput, latency and dropped requests respond to increasing traffic.
ShopEasy App Preview Provide a mobile app preview (ShopEasy) that changes according to the flag value received by the Client SDK.
Fault Injection & Fallback Allow fault injection (storage, broker, SSE, cache or SDK failure, traffic spike, network delay) to demonstrate eventual consistency and stale-cache fallback.
Automated Acceptance Verification Verify the design rules with an automated acceptance test suite.
2.3 Scope and Intended Users

The project includes a browser-based simulation engine, an interactive SVG architecture canvas, live charts, a phone preview, component tuning, fault injection, an event log and a test suite. It does not deploy real cloud servers, Kafka, Redis, a real database or real network sockets; all distributed behaviour is modelled inside the simulation engine. The intended users are computer science and system design students, and evaluators who want to inspect failures and recovery without paying for cloud services.

4. Component Design & Specifications

Capacity ratings, base latencies, and architectural responsibilities

Table 1. Components, capacities and base latencies

Component Zone Capacity Base Latency Responsibility
Client Instances Evaluation 12,000 req/s 0.1 ms Apps, browsers and services that request flag evaluations
Load Generator Evaluation 10,000 req/s 0.2 ms Creates simulated request traffic and represents offered load
Client SDK Evaluation 8,000 req/s 0.3 ms Embedded library that reads cache and listens for SSE updates
Local Flag Cache (L1) Evaluation 12,000 req/s 0.2 ms In-memory hash table with O(1) lookup
SDK Evaluation Engine Evaluation 6,000 req/s 0.5 ms Applies rules and returns ON, OFF or a variant
Configuration Service Control plane 500 req/s 8.0 ms Admin API to create, validate and toggle flags
Cloud Configuration Storage Control plane 400 req/s 15.0 ms Durable store of the latest flag state
Pub/Sub Broker Control plane 2,500 ev/s 5.0 ms Publishes flag update events
SSE Update Server Control plane 4,000 push/s 4.0 ms Keeps open connections and pushes updates
Monitoring and Telemetry Monitoring 2,000 req/s 2.0 ms Collects metrics and tracks cache hit rate and health
4.1 Configuration Service & Cloud Storage

Represents administrative UI/API handling flag updates. Cloud Storage represents durable datastores (e.g. DynamoDB / PostgreSQL). Storage failures abort the update before publication occurs.

4.3 Pub/Sub Broker & SSE Server

Pub/Sub handles event bus decoupling. SSE Server streams events to connected SDKs. Broker or SSE outages freeze propagation, but client evaluation continues uninterrupted using cached data.

5. Data Flow & Failure Handling Matrix

Control-plane flow, hot data-plane flow, and component fault strategy

Table 2. Behaviour of the system when a component fails

Failed Component Effect on Updates (Cold Path) Effect on Evaluations (Hot Path)
Configuration Service Update is rejected immediately None. Evaluations continue from the cache.
Cloud Storage Write fails with HTTP 503, update is aborted, no event published None. The phone keeps the cached flag.
Pub/Sub Broker Value is saved but not published. Status is blocked (Pub/Sub). None. Clients are stale but evaluate at full rate with 0 errors.
SSE Server Event is published but not streamed. Status is blocked (SSE). None. After restore, the backlog is pushed to clients.
Client SDK / Local Cache Updates cannot be applied Evaluation stops. Throughput is 0 and error rate is 100%.
Traffic above capacity None Capacity exceeded; successful throughput limited, excess requests dropped.

10. Advantages, Limitations & Future Scope

Strengths of decoupled evaluation and production roadmap

10.1 Key Advantages
  • Fast evaluation: In-memory lookup takes ~1.3 ms.
  • High availability: Evaluations survive storage/broker crashes.
  • Low database load: Control plane sees only ~2 req/s under high traffic.
  • Push updates: SSE delivers updates in ~32.5 ms without polling.
10.2 Limitations & 10.3 Future Scope
  • Simulation model: Browser engine without physical sockets.
  • Future Scope: Browser state persistence via IndexedDB.
  • Real Adapters: Add actual REST endpoints and Redis Pub/Sub.
  • Targeting Engine: Support percentage rollouts based on user ID hashing.

11. Conclusion

Final engineering takeaway

This project built an interactive virtual lab for a low-latency distributed feature flag service. Its main contribution is the clear separation of the hot evaluation path from the cold control-plane path. Flags are evaluated from an in-memory cache inside the Client SDK, while configuration changes travel through the Configuration Service, Cloud Storage, the Pub/Sub Broker and the SSE Update Server.

The simulation engine models 10 components and illustrates capacity limits, failures and recovery. At baseline, it reports approximately 1.3 ms evaluation latency and 32.5 ms configuration propagation latency. Within this scope, it is useful for learning bottlenecks, eventual consistency, client-side caching and fault tolerance.
