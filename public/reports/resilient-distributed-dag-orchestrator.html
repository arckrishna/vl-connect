1. Abstract & Scope

Executive summary, design targets, and terms

The Resilient Distributed DAG Orchestrator (ORBIT) turns a raw cloud queue and an auto-scaling worker fleet into a dependency-aware workflow engine. A control plane tracks every DAG and every task as an explicit state machine, records each transition in a write-ahead log (WAL), and recovers from crashes by replaying that log from the last checkpoint. Workers are stateless and idempotent, so the queue's at-least-once delivery yields effectively-once task effects.

The design targets three primary guarantees: crash recovery of workers and the control plane, at-least-once execution with idempotent replay, and linearizable reads of DAG status. This is a Phase 1 architectural design report specifying requirements, architecture, data model, state machine, control pathways, failure handling, security, and a validation plan. The guarantees are design targets to be demonstrated by Phase 2 implementation and fault injection tests.

2. Introduction & Objectives

Background, problem statement, and project scope

Cloud queues such as SQS and Pub/Sub deliver messages, and auto-scaling groups add compute, but neither understands task dependencies, ordering, or partial failure. A pipeline that simply fires tasks onto a queue cannot tell when a downstream task is safe to start, cannot resume correctly after a crash in the middle of a DAG, and offers no consistent view of where a workflow stands. Typical uses are data pipelines, build and release workflows, batch ML jobs, and multi-step processing.

Problem Statement

"How can unordered, independently retryable queue messages be turned into a resumable, dependency-aware workflow engine that survives worker and control-plane crashes without silently losing or double-applying work?"

Primary Objectives

01.
Dependency Execution: Release tasks only after all upstream dependencies have SUCCEEDED or SKIPPED.
02.
Durable State Machine: Track every DAG and task through explicit state transitions persisted durably.
03.
Deterministic WAL Recovery: Rebuild control-plane state from log replays starting from the last checkpoint.
04.
Lease & Failure Detection: Detect dead workers via heartbeat/lease expiration and safely reschedule tasks.
05.
Effectively-Once Processing: Combine at-least-once message queues with worker idempotency keys.
06.
Linearizable Status Reads: Serve workflow progress queries from a strongly consistent database.

To prevent split-brain updates from a zombie or deposed leader, every leader election increments a monotonic epoch counter. The State Store rejects any write carrying an epoch lower than the current active token.

7. Consistency & Correctness

Safety mechanisms closing raw queue concurrency gaps

Transactional Outbox Pattern

State change, WAL record, and message outbox write commit in a single database transaction. Eliminates discrepancies between store state and queue messages.

Monotonic Epoch Fencing

Leader promotion increments an epoch counter. Any write bearing a stale epoch is atomically rejected by the State Store.

Stable Idempotency Keys

Task outputs are hashed by task_id + input_hash. Redelivered messages hit the deduplication table and are discarded before scheduling downstream tasks.

Pure Transition Function

State recovery replays log events using recorded timestamps and backoff jitter saved inside WAL entries, maintaining complete determinism.

8. Failure & Edge-Case Handling

Fault tolerance matrix across infrastructure failures

Scenario Detection System Response Data & Safety Impact
Worker crash mid-task Missed heartbeat / Lease TTL expiry (30s) Lease revoked; task returned to READY & re-enqueued. No data loss; task re-executes idempotently.
Control-Plane crash Lost leader lease / Liveness probe failure Standby promoted under new epoch; replays WAL from last checkpoint. No state loss; rebuilt state equals pre-crash state.
Deposed leader write attempt Stale epoch on write transaction State store rejects transaction write. No split-brain updates possible.
Poison Task (Exhaustive Retries) Attempt count exceeds max_attempts Moved to DLQ; dependents marked BLOCKED. Isolated; requires operator requeue/skip.

9. Security, Observability & Operations

Threat model, structured metrics, and runbooks

Least-Privilege IAM

Workers can only take/renew task leases and publish event messages. They have no direct access to alter DAG state tables.

Structured Observability

Log entries contain structured JSON carrying dag_id, task_id, attempt_id, epoch, LSN for unified tracing.

Operator Overrides

BLOCKED DAGs can be manually requeued, skipped, or cancelled. Every operator override records identity and reason in the WAL.

10. Validation & Testing Plan

Automated fault-injection harness and benchmark suite

Worker Kill Injection: Terminate workers mid-execution to verify lease revocation and exact single execution.
Split-Brain Partition: Pause active leader, promote standby to epoch+1, and confirm old leader write rejections.
Replay Equivalence: Rebuild State Store strictly from WAL log replay and verify exact match with live state.
Duplicate Delivery: Inject duplicate SQS queue messages and assert zero redundant execution calls.

12. Conclusion & References

Architectural takeaway & academic citations

The Resilient Distributed DAG Orchestrator adds a thin, carefully specified WAL-backed state machine layer over a best-effort queue and a stateless worker fleet. The layer supplies what raw queue primitives lack: dependency awareness, deterministic crash recovery, and idempotent execution. Phase 1 fixes the requirements, architecture, data model, state machine, and test plan; Phase 2 implements the harness to prove guarantees under fault injection.
