CortexAI – Edge-Based Distributed Rate Limiting Middleware

Abstract

Modern web applications rely on APIs and multiple backend services to handle user requests efficiently. As the number of users and incoming requests increases, these services may experience excessive traffic, which can affect system availability, response time, and resource utilization. Rate limiting is an important technique used to control the number of requests a user can make within a specified time interval. It helps prevent excessive API usage, protects backend services from unnecessary load, and supports fair usage of application resources.

CortexAI – Edge-Based Distributed Rate Limiting Middleware is a web-based system designed to demonstrate API request control within a service-oriented application architecture. The system uses a Node.js and Express.js backend, with a gateway responsible for routing requests to appropriate backend services. Authentication is handled through session-based validation, while Redis is used to store session information and shared rate-limit counters across distributed instances.

Chapter 1: Introduction

Background, Problem Statement, Objectives, and Scope

1.1 Background

API-based applications commonly divide functionality across services. When many requests reach a service in a short period, they may consume compute capacity, increase latency, or reduce availability for other users. Rate limiting restricts the number of requests permitted for a user, route, or operation during a specified time window. CortexAI is a modular AI platform with services for authentication, chat, AI-agent workflows, and billing. Its gateway is the common entry point for several backend routes, and Redis provides shared session and rate-limit data.

1.2 Problem Statement

Applications that expose multiple APIs may receive excessive requests from individual users or clients. Without suitable request controls, repeated requests can increase service workload, consume available resources, and affect the responsiveness of the application. The project focuses on understanding and documenting rate-limiting mechanisms within CortexAI. The rate limiter in the supplied code tracks requests using user-specific and agent-specific counters, applies configured request limits, and rejects requests that exceed those limits with HTTP 429 status codes.

1.3 Objectives

Study the architecture of CortexAI and the role of its API gateway.
Understand how client requests are routed to backend microservices.
Examine the existing Redis-based rate-limiting mechanism.
Explain the fixed-window counter algorithm and its TTL expiration behavior.

1.4 Scope of the Project

The report covers the CortexAI repository with emphasis on the gateway, Agent service, Redis integration, and rate-limit configuration. It documents existing implementations and establishes rigorous test suites.

2.1 Overview of CortexAI & Existing Limitations

CortexAI uses a React/Vite frontend and Node.js/Express services. The gateway routes authentication requests to the Auth service and protected chat, agent, and billing requests to their respective services. The Agent service coordinates specialized workflows such as chat, coding, PDF, presentation, image, vision, and search tasks. The rate-limit check is located in the Agent service flow.

Chapter 3: System Design and Architecture

Architecture, Request Workflow, Fixed-Window Algorithm, and System Flowchart

3.1 System Architecture & Flowchart

CortexAI follows a gateway-and-microservices structure. The frontend communicates with the gateway, which routes requests to Auth, Chat, Agent, and Billing services. Redis stores session information and the Agent service's rate-limit counters.

3.2 Rate-Limiting Algorithm

The Agent rate limiter implements a Redis fixed-window counter. Limits are configured per agent category. When a request arrives, the code creates a key rate:<userId>:<agent> and increments it using INCR. When the count first becomes one, a 60-second expiry (EXPIRE) is applied. If the count exceeds the maximum, an error with HTTP status 429 is raised.

Chapter 6: Conclusion and Future Scope

Conclusion, Limitations, and Future Roadmap

6.1 Conclusion

CortexAI demonstrates a service-oriented backend with an Express gateway, protected routes, Redis-backed session storage, and a fixed-window rate limiter in the Agent service. The limiter uses per-user and per-agent counters with a 60-second expiry and returns structured HTTP 429 errors when limits are exceeded.

6.2 Future Scope

Gateway-Wide Policies Apply rate limiting uniformly at the API gateway entry point rather than individual agent services.
Atomic Lua Scripting Combine counter increments and TTL expiration into atomic Redis Lua scripts.
Sliding Window Algorithms Compare fixed-window with sliding-window log and token bucket algorithms.
Distributed Load Testing Conduct multi-instance cluster testing under high concurrent request volume.
