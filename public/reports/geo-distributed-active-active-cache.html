1. Abstract

Executive summary, key empirical findings & virtual lab deliverables

GeoCache is a design and virtual lab for a cache cluster that runs in three cloud regions (Mumbai, Frankfurt, and N. Virginia) and accepts writes in every region. Keys are placed on a consistent hashing ring, updates travel between regions asynchronously, and concurrent updates are merged with conflict-free replicated data types (CRDTs).

The implemented deliverable is an interactive browser-based virtual lab with three experiments: a hash ring simulator, a multi-region replication simulator with link partitions, and a CRDT workbench. A fourth tab holds a quiz and an automatic lab journal.

Measurements taken from the lab's own code show that consistent hashing moves 8% to 13% of keys when one node joins a cluster of 6 to 9 nodes, against 85% to 90% for modulo hashing. Raising virtual nodes from 1 to 128 lowers the load spread across six nodes from 72% down to 6%. A plain counter loses 2 of 3 concurrent increments, while the G-Counter and PN-Counter keep all of them. After a simulated partition is healed, all three regions converge to identical data. Deployment on real cloud VMs is specified in this report as the next phase and is not claimed as completed work.

Key Movement Efficiency

2. Introduction, Problem Statement & Objectives

Multi-region latency dilemma and specific evaluation goals

A cache keeps frequently used data in memory so that applications avoid slow database reads. When users are spread across continents, a single cache in one region forces distant users to pay the full network round trip on every request. The round trip between Mumbai and N. Virginia is about 186 ms in the lab's model, far above the roughly 2 ms a local cache needs.

The usual remedy is to run a cache cluster in several regions. The design question is then how to let each region write. A single primary region keeps data simple but makes remote writes slow and leaves the system read-only if that region fails. An active-active design lets every region accept writes locally, which keeps latency low and keeps the system available during a network partition. It does so at the price of eventual consistency: two regions can change the same key at the same time and must reconcile afterwards.

2.1 Problem Statement

"Design and demonstrate a geo-distributed, active-active cache cluster running on cloud compute VMs in multiple regions connected by inter-region peering, using a consistent hashing ring for key placement and CRDTs for conflict resolution, and provide a virtual lab through which the behaviour can be explored."

2.2 Core Project Objectives

1. Consistent Hashing Ring Show how a consistent hashing ring places keys and how few keys move when nodes join or leave.
2. Partition Convergence Show how writes accepted in different regions replicate, diverge during a partition, and converge after healing.
3. CRDT Reconciliation Show how CRDTs (G-Counter, PN-Counter, LWW-Register, OR-Set) resolve conflicts vs plain counter data loss.
4. Quantitative Analysis Quantify placement quality, rebalancing cost and write latency for the active-active topology.
5. Feasibility Assessment Assess technical, economic and schedule feasibility of deploying the cluster on real multi-region VMs.
6. Virtual Educational Lab Deliver the lab with theory, procedure, experiments, a quiz and a journal for teaching.

3. Theoretical Background

Consistent hashing, active-active CAP trade-offs, and CRDT math

3.1 Consistent Hashing & Ring Topology

Every node and every key is hashed into the same circular space of 2^32 positions. A key is stored on the first node found moving clockwise from the key's position. With standard hash(key) mod N placement, changing N changes the owner of almost every key. On a ring, a new node takes over only the arc just before its own position, so the expected fraction of keys that move is close to one node's fair share:

$$\mathbb{E}[\text{keys moved}] \approx \frac{K}{N+1}$$

Here K is the number of keys and N the node count before the change. One position per node gives an uneven split, so each node is hashed many times. These extra points are virtual nodes. They average out the arc lengths and also spread a failed node's keys over many peers instead of one single neighbour. Dynamo-style systems extend placement to a preference list: the next distinct nodes clockwise hold replicas. Skipping nodes in a region that already holds a copy makes the copies region-aware.

3.2 Active-Active Replication and the CAP Trade-off

When a network partition occurs, a system must choose between consistency and availability. An active-active cache chooses availability: each region keeps accepting reads and writes, and updates queue up for the unreachable region. When the link returns, the queued updates are delivered and the replicas converge. This is eventual consistency. A strongly consistent alternative (such as a majority quorum) forces every write to wait for cross-region round trips.

3.3 Conflict-Free Replicated Data Types (CRDTs)

A state-based CRDT merges two replica states with a function $m(a,b)$ that is commutative, associative, and idempotent. Replicas that have received the same set of updates then hold the exact same state, whatever the delivery order, batching, or duplication:

m(a, b) = m(b, a)   |   m(m(a, b), c) = m(a, m(b, c))   |   m(a, a) = a
CRDT Type State Structure Merge Function Reconciliation Behaviour
G-Counter One count per replica Per-replica maximum Counts that only grow. Value is the sum across replicas.
PN-Counter Two G-Counters (P and N) Merge each side independently Counts move both ways. Value is sum(P) minus sum(N).
LWW-Register Value with timestamp & replica ID Keep higher timestamp (tie-break ID) Always converges but drops one of two concurrent writes. Clock dependent.
OR-Set Added elements with unique tags + removed tags Union of tags Observed-Remove Set: A remove deletes only seen tags, so concurrent adds survive.

4. Feasibility Study

5-dimension project assessment and fallback lab design

The project is feasible on all five dimensions assessed. The primary dependency that can alter the multi-region VM deployment phase is cloud budget, which features a no-cost fallback design.

Dimension Verdict Assessment Basis
Technical Feasible Consistent hashing, asynchronous replication and state-based CRDTs are standard documented techniques. Virtual lab implements all three in browser JS. Cloud VPC peering handles connectivity.
Economic Feasible with cap Three small compute VMs running part-time cost a few USD per month plus inter-region transfer. Free-tier credits can cover it; fallback runs on one host with emulated latency.
Operational Feasible Basic Linux, networking, and scripting required. Open-source tooling and synthetic test data eliminate licensing and privacy liabilities.
Schedule Feasible 10-week execution plan with virtual lab phase completed first. Deployment, physical measurements, and report finalization remaining.
Risk Acceptable Main risks include clock skew, cloud budget overrun, and misinterpreting simulation vs real VM data. Mitigations provided for each.

Fallback Emulated Architecture (Linux tc netem)

If paid multi-region cloud instances are unavailable, run six cache processes on a single host. Use Linux traffic control (tc netem) to add delays matching the inter-region RTT matrix between process groups standing for regions. The ring, replication stream, and CRDT engine code remain identical.

6. Subsystem Responsibilities

System architecture components and modular responsibilities

Hash Ring Component

Maps keys to owner nodes and produces the ordered list of replica nodes across distinct geographical regions.

Cache Node Engine

Stores key values in memory, applies local writes, broadcasts state updates to peer regions, and merges incoming state.

Replication Stream

Carries CRDT state updates between regions over peering links, maintaining an outbound queue per unreachable peer during partitions.

CRDT Layer

Defines state-merge algebra (G-Counter, PN-Counter, LWW-Register, OR-Set) ensuring eventual consistency across asynchronous networks.

8. Conclusion

Final summary of results

The GeoCache project demonstrates how consistent hashing, active-active asynchronous replication, and state-based CRDTs combine to deliver a fault-tolerant, low-latency multi-region caching system. By trading immediate global consistency for eventual consistency, local reads and writes execute in ~2ms while ensuring deterministic convergence upon network partition healing.
