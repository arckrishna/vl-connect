1. Abstract

Executive summary, design goals, and simulator notes

This report presents the system software design for a Dynamic Layer 7 (L7) API Gateway and Reverse Proxy. The gateway provides one single, secure HTTPS entry point for web, mobile, and external clients. It verifies JSON Web Tokens (JWTs), matches requests against configurable routing rules, forwards valid requests to private User, Product, or Order services, and relays backend responses seamlessly back to clients.

Routing configuration is stored outside the gateway so that validated changes can be loaded dynamically in real time without restarting the gateway process. Sensitive values such as signing keys and API credentials are retrieved directly from a cloud Secret Manager. The design also specifies network isolation, connection/read timeouts, controlled error responses, structured logging, and multi-instance active deployments behind a load balancer.

Verification Note: The architecture diagram describes the intended technical design. The accompanying BreakScale simulator topology represents the main components and connections. A diagram or component label alone does not prove that JWT verification, Redis-backed configuration reload, or runtime path matching is active in the simulator—these behaviors are verified through implementation and structured validation testing.

1. Introduction

Context & advantages of Layer 7 gateways

Microservice architectures divide monolithic business capabilities into independent, smaller services. Without a centralized API gateway, client applications must discover and keep track of individual service endpoints, while each backend microservice is forced to duplicate authentication, rate limiting, routing, and error-handling logic. An L7 gateway centralizes these cross-cutting operational responsibilities while allowing backend services to remain decoupled and independently deployable.

Unlike a Layer 4 (L4) load balancer—which routes TCP/UDP connections using transport-level IP addresses and ports—an L7 gateway inspects HTTP methods, URL paths, headers, and verified identity claims. Combining this deep inspection capability with reverse proxying and hot-reloadable routing rules allows cloud administrators to modify service destinations on the fly without forcing clients to change their base URL or experience service downtime.

2. Problem Statement

Challenges of directly exposing microservices

Architectural Vulnerabilities of Direct Exposure

Directly exposing individual backend microservices to public networks introduces severe security vulnerabilities, code duplication, fragile deployments, and poor operational visibility.

Larger Attack Surface Exposed backend services can be targeted directly from public networks.
Duplicated Authentication Every service repeats JWT verification and identity checking logic.
Rigid Routing & Restarts Changing an endpoint address requires client code updates or service restarts.
Credential Leakage Risk Hard-coded secrets in config files risk accidental repository exposure.
Inconsistent Handling Slow or dead backends cause unhandled stack traces and varied client errors.
Fragmented Observability Independent logs make tracing end-to-end request latencies difficult.

3. Objectives & Scope

Core goals and boundary definitions

3.1 System Objectives

O1 Provide a single HTTPS entry point for all client web, mobile, and external applications.
O2 Validate JWT signatures, expiry, and required claims before forwarding protected requests.
O3 Route requests dynamically using URL path prefixes, HTTP methods, and custom headers.
O4 Load validated routing updates on the fly without restarting the gateway process (hot reload).
O5 Retrieve signing keys and API credentials from a managed Secret Manager.
O6 Keep User, Product, and Order microservices isolated inside a private network segment.
O7 Apply explicit connect/read timeouts and return controlled HTTP failure responses.
O8 Support multi-instance gateway deployments behind a load balancer for high availability.

3.2 Scope Boundaries

In Scope HTTPS ingress, JWT verification, path routing, reverse proxying, configuration schema validation & hot reload, secret fetching, structured logging, health checks, timeouts, and standard error handling.
Out of Scope Token issuance (OAuth2/OIDC identity provider implementation), full user identity management UI, and internet-scale performance tuning beyond academic project scope.

5. Request Processing Flow

9-step end-to-end request lifecycle

1 Client sends HTTPS request to the public gateway endpoint.
2 Rate limiter evaluates request volume against bucket policy (rejects 429 if exceeded).
3 Load balancer selects a healthy gateway instance (Gateway 1 or Gateway 2).
4 Gateway extracts Bearer token from Authorization: Bearer <JWT> header.
5 JWT module validates token signature using Secret Manager key, checks expiry and claims.
6 Dynamic router matches HTTP method and URL path prefix against active routing table.
7 Reverse proxy forwards request to private backend with timeouts and correlation ID.
8 Backend service processes request and returns HTTP response to reverse proxy.
9 Gateway relays response to client and logs metadata (Latency, Status, Route ID).

6. Dynamic Routing & Hot Reload Protocol

Zero-downtime routing updates and schema validation

The initial routing table maps incoming request path prefixes to private backend microservices:

Path Pattern Destination Service Example Request
/users/* User Service GET /users/42
/products/* Product Service GET /products/123
/orders/* Order Service POST /orders
Atomic Hot-Reload Protocol:
  1. Administrator pushes route update to Redis/Config Store.
  2. Gateway instances receive publication event or fetch updated JSON configuration schema.
  3. Gateway parses configuration and validates destinations against an allowable subnet whitelist.
  4. If schema validation succeeds, gateway constructs a new routing table object and atomically swaps the active pointer.
  5. If validation fails, the candidate config is rejected and the last-known-good (LKG) table remains active.

7. Auth, Authz & Secret Management

JWT verification rules and cloud Secret Manager integration

7.1 JWT Verification Rules
  • Accept tokens exclusively via Authorization: Bearer <JWT> header.
  • Verify signature using trusted Secret Manager public keys and explicitly allowed algorithms (RS256/HS256). Reject alg: "none".
  • Validate expiration (exp), Not Before (nbf), Issuer (iss), and Audience (aud).
  • Return HTTP 401 Unauthorized for missing/expired tokens; return HTTP 403 Forbidden for missing permissions.
7.2 Secret Manager Integration
  • Retrieve signing keys, API credentials, and internal TLS certificates dynamically from cloud Secret Manager.
  • Apply least-privilege IAM roles to gateway instances.
  • Cache secrets in local gateway memory with TTL refresh policy; redact secrets from logs.
  • Fail closed if Secret Manager is unreachable and cache is stale.

8. Network & Security Controls

Security matrix and boundary enforcement

Security Concern Architectural Control
Client-to-Gateway Traffic Enforce HTTPS/TLS 1.3; redirect or drop HTTP plain traffic.
Backend Exposure Isolation Place services in private subnets; allow ingress only from gateway security groups.
Administrative Access Require MFA, RBAC permissions, and audit log all configuration updates.
Configuration Tampering Validate JSON schema, enforce destination allow-lists, and keep last-known-good backup.
Sensitive Header Sanitization Strip incoming untrusted identity headers (e.g. X-User-ID) before proxying.

9. Reliability, Scalability & Failure Matrix

Fault tolerance behaviors across 10 failure scenarios

Failure Scenario Expected Gateway Response
Invalid JWT Return HTTP 401 Unauthorized; do not forward request.
Authenticated but Unauthorized Return HTTP 403 Forbidden; block backend access.
No Route Match Return HTTP 404 Not Found or custom gateway routing error.
Backend Unavailable Return HTTP 503 Service Unavailable; keep gateway instance healthy.
Backend Slow / Unresponsive Enforce read/connect timeout (e.g. 2s); return HTTP 504 Gateway Timeout.
Invalid Route Configuration Reject candidate schema update; retain last-known-good (LKG) table.
Config Store Unavailable Continue operating on in-memory routing table; trigger alert.
Secret Manager Down Use cached secrets within TTL policy; fail closed if cache expires.
Gateway Instance Crash Load balancer health check removes dead pod; traffic shifts seamlessly to healthy instances.

10. Capacity & Performance Evaluation

Analysis of BreakScale simulation metrics

The BreakScale simulator snapshot records ~7.8 requests/second sent by clients and ~7.8 requests/second served by the load balancer. Gateway 1 handles 6.7 requests/second passed while Gateway 2 records zero passed requests during that specific snapshot window. The client panel also reports a ~13% failure rate.

Performance Investigation Steps:
  • Inspect load balancer algorithm (Verify if round-robin vs sticky sessions caused Gateway 2 starvation).
  • Verify Gateway 2 readiness probe health status in simulator runtime.
  • Benchmark throughput, P50/P95/P99 latency percentiles, error rate, and queue depths under gradual load escalation.

13. Risks & Risk Mitigations

Risk register and architectural countermeasures

Invalid Route Config Push Mitigation: Enforce JSON schema validation, destination subnet allow-listing, and atomic LKG fallback.
Secret Manager Outage Mitigation: In-memory key caching with strict TTL decay; fail closed if cache expires.

16. Conclusion & References

Final engineering summary and standards bibliography

The Dynamic L7 API Gateway and Reverse Proxy design provides a comprehensive system architecture for centralizing client request ingress, JWT authentication, route matching, reverse proxying, cloud secret retrieval, and failure recovery across private User, Product, and Order microservices. Externalized route configuration paired with atomic schema validation and zero-downtime hot reload distinguishes this system software design from static reverse proxies.
