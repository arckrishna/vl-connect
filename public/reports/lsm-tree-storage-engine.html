1. Abstract

Core executive summary & system goals

Modern applications generate large amounts of data that must be stored reliably and cost-effectively. Object storage systems provide durable and scalable storage for large files and data objects, but they are not designed to behave like traditional databases that support frequent small updates, low-latency reads, and efficient range queries. Directly storing every database update as an independent object can create high request overhead, inefficient reads, and expensive metadata management.

This project proposes an LSM-Tree (Log-Structured Merge-Tree) Storage Engine over Object Storage. The engine accepts key-value writes, records them in a write-ahead log, and buffers recent updates in memory. When the memory buffer reaches a configured threshold, the engine sorts and flushes the data into immutable, sorted table files called SSTables. These files are stored in an object-storage backend. Background compaction merges overlapping or older SSTables, removes obsolete versions where safe, and improves read efficiency.

The system separates the database engine's logical operations from the underlying storage provider. A storage interface can be implemented over a local filesystem for development and an S3-compatible object store for deployment. An in-memory index, block metadata, Bloom filters, and a manifest help the engine locate data while avoiding unnecessary object reads. The design also considers consistency, crash recovery, object naming, versioning, and the cost of object-store requests.

The primary objective is to demonstrate how an LSM-Tree can provide database-like key-value operations while using object storage as the durable data layer. The project is intended as an educational prototype; production deployment would require further work on concurrency, distributed coordination, durability guarantees, observability, and failure recovery.

2. Introduction & Objectives

Context, architectural motivation, and project goals

Applications such as analytics platforms, event-processing systems, log services, and IoT platforms often need to persist a large volume of records. A traditional database may provide convenient updates and queries, but its storage and compute costs can become significant when datasets grow. Object storage offers low-cost capacity, high durability, and elastic scaling, making it attractive for storing large immutable data files.

However, object storage typically exposes operations such as PUT, GET, and DELETE on complete objects rather than efficient in-place updates to arbitrary byte ranges. A database engine that attempts to update a single object for every small change may incur excessive write amplification, network traffic, and request costs. Reading many small objects to answer one query can also lead to high latency.

An LSM-Tree addresses write-heavy workloads by converting random writes into sequential, batched writes. Incoming updates are first recorded in a write-ahead log (WAL) and held in an in-memory structure. Once the memory structure fills, its sorted contents are written as an immutable SSTable. Multiple SSTables may represent different versions of the same key. Compaction periodically merges files and reconciles these versions.

2.1 Problem Statement

"How can a key-value storage engine support efficient write and read operations over object storage, while minimizing object requests and data transfer, preserving updates across crashes, and managing immutable data files as the dataset grows?"

2.2 System Objectives

LSM Architecture Build key-value storage engine based on Log-Structured Merge-Tree principles.
Write-Ahead Log (WAL) Maintain write durability for crash recovery prior to SSTable flushing.
Memtable Buffering Buffer writes in sorted memory buffers and flush immutable SSTables.
Object Abstraction Store SSTables and manifests through a uniform object storage interface.
Core Operations Full support for key-value PUT, GET, and tombstone DELETE requests.
Read Optimization Block indexes and probabilistic Bloom filters to reduce S3 HTTP calls.
Compaction Engine Merge overlapping SSTables, drop tombstones, and prune stale versions.
Manifest State Manager Maintain explicit database state metadata and file level tracking.

4. Storage Engine Core Deep Dive

Detailed component engineering and data structure specification

4.1 Overview

The LSM-Tree Storage Engine is the central component of the project. It transforms frequent small key-value updates into batches of sorted immutable files, which are suitable for object storage. Instead of modifying an existing SSTable in place, the engine creates new SSTables and later merges them through compaction.

1. Write Handling Records updates in WAL and exposes recent values via memtable.
2. Flush & Persistence Converts memory-resident data into sorted SSTables and uploads to S3.
3. Read Path Searches memory first, then checks Bloom filters & block indexes.
4. Compaction Merges files, resolves latest key versions, and prunes tombstones.
5. Metadata & Recovery Maintains active Manifest and replays WAL during cold restart.

4.2 Write Path and Memtable

When a client sends a PUT operation, the engine first validates the key and value. It appends the operation to the WAL before acknowledging the write, according to the configured durability policy. The operation is then applied to the memtable, where the latest value for the key becomes immediately visible to reads.

A DELETE operation is represented as a tombstone rather than immediately removing every older copy of the key. The tombstone ensures that an older value in an SSTable is not mistakenly returned after a deletion.

// Conceptual Write Pipeline
PUT / DELETE → Append to WAL → Update Memtable → Acknowledge Client
// Memtable Threshold Reached (Flush)
Memtable → Freeze & Sort Entries → Build Index & Bloom Filter → Upload S3 Object → Commit Manifest Metadata

4.3 SSTable Format and Read Operations

An SSTable (Sorted String Table) is an immutable file containing key-value records sorted by key. A simple prototype can use a file format containing a header, sorted data blocks, a block index, optional Bloom-filter data, and a footer with offsets and checksums.

SSTable Binary File Format Layout
[ Header ]
[ Sorted Data Blocks ]
[ Block Index ]
[ Bloom Filter Data ]
[ Footer & Offsets ]

The block index maps key ranges to byte offsets or block identifiers. Rather than downloading an entire large SSTable for every query, the reader first retrieves the required metadata and then fetches the relevant block, if the object-storage API and chosen file layout support range reads. If range reads are unavailable, the engine fetches the full SSTable object and caches it locally.

4.4 Object Storage Integration

The Object Storage Adapter isolates the engine from provider-specific storage APIs. A basic interface exposes operations such as putObject(key, data), getObject(key), getRange(key, start, end), and deleteObject(key).

4.5 Compaction Strategy

Compaction selects SSTables, reads and merges their sorted entries, and writes a new SSTable containing the appropriate versions. For each key, it keeps the newest valid version according to the sequence-number ordering rules. Tombstones are safely discarded when no older values exist in lower levels.

4.6 Manifest & Recovery

The manifest records active SSTables, levels, key ranges, and generation IDs. During cold startup, the engine loads the manifest and replays eligible WAL records to reconstruct the exact un-flushed memory state.

5. Data Flow, Consistency & Failure Handling

Durability guarantees, lifecycle flows, and fault-tolerance matrix

5.1 Read/Write Consistency

Writes acknowledged after WAL durability step. Reads prioritize highest sequence number (Memtable > SSTables L0 > L1).

5.2 Flush Lifecycle

Memtable freezes, converts to SSTable, uploads under unique object key, updates Manifest, and truncates WAL.

5.3 Compaction Flow

Merges key ranges, resolves tombstones, uploads target level SSTable, updates Manifest generation, and deletes obsolete objects.

5.4 Failure Handling & Performance Considerations

Failure / Scenario Engine Recovery Mechanism
Network Timeout on Upload Retry with unique object key and idempotent strategy; never commit incomplete file.
Crash During Flush Load last valid manifest generation; replay eligible uncommitted WAL records.
Crash During Compaction Keep previous manifest generation active until new output files are fully uploaded and committed.
Corrupt SSTable Block Detect via footer block checksum; report explicit read failure rather than silent corruption.
Excessive Object Overhead Batch writes into SSTables, cache frequently accessed metadata, and leverage Range GETs.

* Design Note: Object storage reduces cost and scales infinitely, but introduces network latency compared with local high-speed NVMe storage. Optimizing batch size, block caching, and range requests is paramount.

7. Advantages & Future Scope

Strengths of the architecture and roadmap for production readiness

7.1 Architectural Advantages

Write Efficiency Batches small updates into sequential immutable writes, drastically reducing S3 PUT overhead.
Scalable Capacity Uses cloud object stores for infinite, cost-effective data retention.
Separation of Concerns Decouples logical database execution from physical cloud storage provider APIs.
Minimized Request Overhead Bloom filters and sparse indexes avoid unnecessary remote object downloads.

7.2 Future Scope & Production Roadmap

1. Block Compression Implement ZSTD/Snappy compression for reduced network bandwidth.
2. Block & Metadata Cache Add LRU memory caching for frequent GET lookups.
3. Multi-part Uploads Support resilient multipart S3 uploads for large SSTables.
4. Observability Metrics Track Read/Write Amplification and S3 request counters via Prometheus.
5. Distributed Coordination Integrate Raft / Etcd for multi-node consensus over object storage.
6. Leveled Compaction Implement strict Leveled Compaction to bound read amplification.
08

8. Conclusion

Summary & engineering takeaway

The LSM-Tree Storage Engine over Object Storage demonstrates how database-style key-value operations can be built on top of an object-storage system. By buffering updates in memory, recording operations in a WAL, flushing sorted immutable SSTables, and merging files through compaction, the engine avoids relying on frequent in-place updates to stored objects.

The architecture combines a memtable, WAL, SSTable reader, Bloom filters, block indexes, manifest metadata, compaction manager, and object-storage adapter. These components work together to support writes, reads, deletions, recovery, and long-term data organization. Unique immutable object names and careful manifest-update ordering help manage the risks associated with interrupted flushes and compactions.

The main contribution of the project is the integration of an LSM-Tree storage model with an object-storage backend, while accounting for the trade-offs introduced by network latency and object request costs. The design can serve as a foundation for learning about storage engines, write amplification, read amplification, compaction, and durable metadata management.
