1. Abstract & Document Map

Executive summary, key terms, and report structural map

TraceLab is a Distributed Tracing Virtual Lab that illustrates how telemetry produced by an application travels through a collection pipeline. The proposed model contains an instrumented service graph (API gateway, order service, payment service, inventory service, and database), OTLP transport over gRPC/HTTP, a least-buffered load balancer, two collector replicas, a trace backend, and a trace explorer.

A separate self-monitoring path represents collector counters and gauges flowing to a Prometheus-compatible metrics backend and dashboard. The lab focuses on sampling, batching, bounded queues, throughput, and component failures. This report explains the core concepts, architecture, processing flow, requirements, experimental procedure, and evaluation metrics. The supplied interface reports a local simulation environment, allowing for rigorous baseline measurement and controlled failure testing.

Keywords: Distributed tracing, OpenTelemetry, OTLP, telemetry pipeline, collector, sampling, batching, bounded queue, observability.

2. Introduction & Problem Definition

Context, problem statement, aim, and core objectives

A modern application request is usually processed by several cooperating components rather than one program. For example, an API gateway may call an order service, which then contacts a payment service, an inventory service, and a database. If a request becomes slow, application logs from one service may not explain where the time was spent. Distributed tracing addresses this limitation by connecting work across services into a trace composed of related spans.

Telemetry must itself be transported and processed. Instrumented services emit spans, an exporter sends them through OTLP, a collector receives and processes them, and an exporter forwards them to a trace backend. At high input rates, collectors can become a bottleneck. Sampling intentionally retains only a subset of traces; batching groups telemetry for export; queues absorb temporary differences between input and output rates; retries handle transient failures.

1.1 Problem Statement

"A distributed application needs an end-to-end view of a request, but its telemetry pipeline has finite processing and buffering capacity. Poor sampling choices can hide work, insufficient collector capacity can create queues and losses, and a slow or unavailable backend can delay exports. TraceLab models these trade-offs so a learner can change the pipeline configuration, inject failures, and analyse how much visibility is retained."

1.2 Aim

To study and simulate a distributed tracing and telemetry collection pipeline, understand how traces flow across microservices and OpenTelemetry Collectors, and evaluate the impact of sampling, batching, collector capacity, and component failures on telemetry collection.

1.4 Scope & Boundaries

The current scope is a browser-based local simulation. The architecture is a learning model rather than a claim that a production OpenTelemetry deployment is running. The report includes no real customer data, credentials, or remote backends.

1.3 Project Objectives

Explain trace IDs, span IDs, and parent-child relationships in multi-service requests.
Describe the role of instrumentation, OTLP, and receiver-processor-exporter pipelines.
Compare how two collector replicas receive and export spans through a least-buffered load balancer.
Observe sampling, batching, bounded queue capacity, and retry/failure behavior.
Interpret collector self-monitoring counters and gauges through a simulated dashboard.
Compare baseline runs with experimental configurations using numeric observations.

3. Theoretical Background

OpenTelemetry fundamentals, span structures, collector pipeline stages

2.1 Traces & Spans

A trace represents the end-to-end path of one request. A span represents an operation. Trace IDs group spans; span IDs identify one span; parent span IDs represent causal relationships.

2.2 Propagation & OTLP

Instrumentation creates spans and propagates trace context to downstream calls. OpenTelemetry Protocol (OTLP) transports telemetry over gRPC/HTTP endpoints.

2.6 Self-Monitoring

Separate dashed path exposes operational metrics (accepted/dropped spans, queue utilization) to Prometheus backends to monitor the observability infrastructure itself.

2.4 Collector Pipeline Stages

Stage Role in TraceLab Questions to Investigate
Receiver Accepts spans arriving over the OTLP endpoint. How many spans enter? Is the receiver overwhelmed?
Processor: Sampling Decides which traces/spans are retained according to model. How does retained-to-generated ratio change with probability?
Processor: Batching Groups spans before export. Does batch size change export frequency, queue occupancy, or delay?
Bounded Queue & Retries Buffers exports during slowdowns and models retry behavior. When does the queue fill? What happens while backend is down?
Exporter Sends telemetry to the trace backend. How many spans are exported, delayed, or dropped?
Self-Monitoring Metrics Reports counters/gauges about the collector pipeline. Can the dashboard reveal saturation before visibility degrades?

Self-Monitoring Pipeline (Prometheus Metrics Flow)

The simulated Prometheus metrics backend periodically scrapes or receives time-series measurements from collector endpoints.

Step 3: Alert & Dashboard

The monitoring dashboard renders real-time queue utilization, exporter error rates, and pipeline throughput graphs for operators.

Failure Modes & Backpressure Mechanics

Queue Saturation & Overflow

When input span rate exceeds export throughput, bounded queues absorb the difference until full, at which point backpressure or span drops occur.

Backend Outage & Retries

If the trace backend becomes unavailable, exporters enter exponential retry loops, filling local bounded queues and triggering drop policies if sustained.

Collector Replica Failure

If collector-2 crashes, the least-buffered load balancer automatically redirects 100% of telemetry traffic to collector-1, testing single-replica capacity.

6. Processing Workflows

Detailed steps for primary trace flow, self-monitoring, and failure modes

5.1 Primary Trace Telemetry Path

  1. Request Entry: A simulated client request enters `api-gateway`.
  2. Instrumentation: Services create spans and propagate trace context downstream.
  3. OTLP Export: Services send telemetry over modeled gRPC/HTTP endpoints.
  4. Routing: Load balancer routes to `collector-1` or `collector-2` based on lowest queue.
  5. Processing: Collector applies sampling/batching, then enqueues to bounded queue.
  6. Export / Retry: Exporter sends batches to backend; outages cause retries/queue growth.
  7. Exploration: Trace explorer displays retained, delivered spans and service trees.

5.3 Behavior Under Pressure or Component Failure

When input rate rises above sustained export throughput, backlog can grow. Increasing queue capacity may absorb a longer temporary outage but also consumes more memory in a real implementation. Batching can increase throughput efficiency while introducing waiting time for batch formation. Sampling reduces the volume retained for downstream processing but also lowers visibility. A collector failure may reduce total capacity or force traffic to the remaining replica. A backend failure may grow queues and trigger retries; if capacity or retry limits are reached, telemetry can be lost.

9. Testing & Evaluation

Test cases TC-01..TC-08 and mathematical evaluation formulas

8.1 Test Cases Verification Table

Test ID Test Condition Expected Behavior to Check
TC-01 Default configuration, no failure Sampled request produces trace with related service spans; counters coherent.
TC-02 Change sampling probability Retained volume changes in the direction implied by setting.
TC-03 Adjust batching size/window Batch/export behavior changes; observations show queue or delay effect.
TC-04 Increase load beyond output capacity Queue pressure becomes visible and configured overflow policy is applied.
TC-05 Backend unavailable, then restored Retry/queue state changes during failure; recovery outcome observable.
TC-06 Collector replica unavailable Load distribution and remaining capacity reflect replica failure.
TC-07 Inspect collector self-monitoring Metric path is visually separate and counters align with events.
TC-08 Reset after a completed run Next run starts from known clean state and does not reuse prior counters.

11. Conclusion & Future Work

Final engineering summary and roadmap

TraceLab provides a structured way to learn the telemetry path that supports distributed tracing. The proposed architecture separates span generation, OTLP transport, load balancing, collector processing, bounded buffering, export, trace exploration, and collector self-monitoring. The project is feasible as a local browser simulation because it can demonstrate design trade-offs without requiring permanent physical server infrastructure.

1. Run Journal Export Downloadable run journal with configurations, seed, state, metrics, and timestamps.
2. Loss Disambiguation Expose separate counters for sampling decisions vs queue drops vs exporter errors.
3. Real Collector Validation Validate scenarios using real local OpenTelemetry Collector binaries and Jaeger/Zipkin.
