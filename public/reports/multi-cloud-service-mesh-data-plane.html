1. Aim

Core goal and project scope target

To design and implement a Multi-Cloud Library Management System using a Sidecar Data Plane across Amazon Web Services (AWS) and Google Cloud Platform (GCP), incorporating service discovery, mutual TLS (mTLS) security, configurable traffic splitting, Redis caching, health checking, failure handling, and performance benchmarking.

mTLS Security

End-to-end mutual TLS encryption between AWS and GCP sidecar proxies.

Traffic Splitting

Weighted routing (e.g. 80% AWS / 20% GCP) controlled via control plane.

Redis Caching

Cache-aside strategy with TTL expiration to offload persistent databases.

02

2. Problem Statement

Challenges in distributed cross-cloud application management

A traditional library management application may experience performance problems when the number of users and requests increases. Deploying the application across multiple clouds can introduce additional challenges related to service communication, routing, security, and failure management.

Repeated database queries can increase response time and database load. Furthermore, when a service becomes unavailable, requests must be redirected to healthy instances whenever possible.

Proposed Solution Architecture

"Therefore, a system is required that supports distributed library services, secure communication, service discovery, configurable traffic routing, caching, health monitoring, and failure recovery. This project proposes a multi-cloud architecture using sidecar proxies, Redis caching, and a control plane to address these challenges."

03

3. Introduction

Service mesh concepts, sidecar pattern, and cross-cloud topology

Modern applications require scalability, availability, security, and efficient communication between distributed services. Cloud computing allows applications to run on different infrastructure providers according to their requirements.

However, deploying an application across multiple cloud platforms introduces challenges such as service discovery, network latency, secure communication, failure recovery, and configuration management.

The Multi-Cloud Library Management System addresses these challenges by distributing library services across AWS and GCP. Each service uses a sidecar proxy to handle networking operations independently of the application's business logic.

Redis is used as a caching layer to store frequently accessed information temporarily. The control plane maintains service information and routing configurations. The proposed system demonstrates how distributed services can communicate securely and efficiently across multiple cloud environments.

6. System Architecture

Detailed component breakdown and architectural diagram

6.1 Client

Represents users interacting with the library application. Can view books, register members, borrow books, return books, and search information. Sends requests through the API gateway.

6.2 Library Application (Gateway)

Entry point for client requests. Identifies the required library operation and forwards traffic to the appropriate service sidecar proxy layer.

6.3 Library Microservices

A. Book Service Add books, view details, update records, search catalog, and check availability.
B. Member Service Register members, retrieve profiles, update member info, and validate credentials.
C. Borrow Service Process borrowing/returns, log transactions, maintain history, and enforce concurrency locks.

6.4 Sidecar Proxy Layer

Runs alongside each service to decouple networking logic: service discovery, request forwarding, traffic routing, mTLS, health checking, retries, and logging.

6.5 Redis Cache

In-memory data store for frequently accessed records. Reduces database reads, lowers database load, and improves sub-millisecond response time.

6.6 Control Plane

Manages service registry, tracks health status, manages traffic weights (e.g. 80/20), distributes routing configs, and handles failover.

6.7 Database Layer (Persistent Block Storage)

Stores permanent records: book details, member info, borrowing logs. Supported engines include PostgreSQL, MySQL, Amazon RDS, DynamoDB, Cloud SQL, or Cloud Firestore over persistent block storage/NVMe.

9. Important System Features

Core architectural capabilities

Service Discovery

Dynamically locates available service instances using registered control plane endpoints without hardcoded IPs.

mTLS Security

Authenticates communicating sidecars and encrypts cross-cloud data in transit using TLS certificates.

Configurable Traffic Splitting

Distributes user requests between AWS and GCP according to configured weights, such as 80% AWS and 20% GCP.

Redis Cache-Aside & TTL

Checks Redis before querying persistent databases. Cache misses trigger database reads and write-back with TTL.

Failure Handling & Health Checks

Continuous health checks identify degraded cloud instances, re-routing traffic to healthy endpoints. Bounded retries and timeouts prevent cascading failures across the mesh.

12. Conclusion

Summary and final architectural takeaway

The Multi-Cloud Library Management System demonstrates how library services can operate seamlessly across AWS and GCP. Sidecar proxies manage communication and routing, the control plane maintains service configuration, and Redis caching reduces repeated database reads over persistent block storage.

Health checks, mTLS, traffic splitting, and failure testing demonstrate important distributed-system concepts. Performance testing is used to evaluate the system's overall effectiveness and latency improvements.
