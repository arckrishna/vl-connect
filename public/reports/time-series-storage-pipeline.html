1. Abstract

Core executive summary & Virtual Lab scope

FlowStore is a time-series storage and ingestion virtual lab designed to demonstrate how incoming records move through a bounded, multi-stage processing pipeline before being persisted as Parquet files. The system models record generation, queueing, validation, partition buffering, chunk formation, writing, and storage metadata. Its purpose is to make throughput, queue pressure, chunk lifecycle, and persistence behavior observable during controlled experiments.

The implementation combines a React and TypeScript interface with a Python FastAPI backend and WebSocket updates. The processing engine uses PyArrow for Parquet output and SQLite for metadata. Docker Compose provides a repeatable local deployment with persistent high-throughput storage engine capabilities. The virtual lab exposes live metrics, event logs, run history, and storage inspection so that system-design trade-offs can be explored.

FlowStore distinguishes implemented local behavior from a scalable target design. The current local pipeline can demonstrate ingestion and persistence behavior; production deployment would require further work on distributed coordination, durable messaging, cloud storage, authentication, and multi-instance recovery. Any capacity figures shown by the simulator should be treated as measurements of the configured run, not universal production guarantees.

Bounded Queueing

Prevents unbounded memory growth during high-rate generation spikes via configurable backpressure.

Columnar Persistence

Uses PyArrow to serialize completed partition chunks into optimized Apache Parquet files.

Live Telemetry

Pushes real-time queue depth, throughput rates, and chunk events via WebSocket connections.

2. Introduction & Objectives

Ingestion bottleneck challenges & explicit system goals

Time-series systems ingest timestamped measurements from applications, devices, services, and infrastructure. These streams can arrive in bursts, and downstream processing or storage may not always keep pace with producers. A robust ingestion design must control memory use, validate incoming data, group records efficiently, and persist results in a format suitable for later analysis.

FlowStore represents this problem as a visible pipeline. Rather than treating storage as a single operation, it separates generation, queueing, processing, buffering, chunk formation, writing, and metadata reporting. This separation helps identify which stage is limiting end-to-end throughput and whether a queue is absorbing bursts or accumulating an unsustainable backlog.

2.1 Problem Statement

"How can a time-series ingestion pipeline accept a configurable stream of records, process and partition them, form storage-efficient chunks, persist them reliably, and expose enough telemetry to identify overload and bottlenecks?"

2.2 System Objectives

Multi-Stage Pipeline Model a multi-stage ingestion pipeline with explicit responsibilities for each stage.
Bounded Queueing Apply bounded queueing to prevent unbounded in-memory accumulation during load spikes.
Record Validation Validate records dynamically and track accepted versus rejected counts in real time.
Partition Buffering Buffer records by partition and form chunks using configurable size and time thresholds.
Parquet & SQLite Persistence Persist completed chunks as Parquet files and record run metadata in SQLite.
Telemetry Visualization Visualize throughput, queue depth, buffer use, chunk activity, and storage outcomes.

4. Ingestion and Chunking Workflow

Processing stages, backpressure control & Parquet serialization

The run begins with configuration of record count, target feed rate, chunk size, writer delay, and invalid-record ratio. The generator emits records until the target is reached or the run is stopped. The queue transfers work to the processor. Accepted records enter partition buffers and are collected into chunks according to the engine's implemented rules. Completed chunks are written to Parquet and reflected in storage metadata.

4.2 Queueing and Backpressure

A bounded queue limits how much work can wait in memory. If producers generate records faster than downstream stages can consume them, queue depth may rise. When capacity is reached, the system's configured queue policy determines whether producers block or records are rejected.

4.3 Chunk Formation & Persistence

Chunking groups records before writing. Larger chunks reduce per-file overhead but increase buffering delay. Smaller chunks become available sooner but create more files and metadata operations. Parquet provides column-oriented analytical efficiency, and SQLite stores run metadata.

5. Concurrency, Scalability and Consistency

Scale-out principles, failure handling matrix, and restart behavior

The local virtual lab helps reason about throughput and queueing, but a single-process prototype does not by itself prove distributed scalability. A production design could separate API instances, ingestion workers, metadata storage, and object storage so each tier can scale according to its own workload.

Table 2. Risk & Failure Design Matrix

Risk / Failure Scenario Design Consideration & Mitigation
Queue Overload Bounded capacity and explicit queue policy; measure backlog and producer waiting times.
Slow Storage Writer Observe persisted throughput and upstream buffer growth; test supported throttling policies.
Write Failure Track failure counts and ensure failed writes are not reported as persisted items.
Stop During Run Cancel generator and background tasks cleanly; define explicit handling for partial buffer chunks.
Metadata / File Mismatch Verify successful files against metadata database entries and reconcile carefully.
Process / Container Restart Use persistent volume mounts and verify previously written Parquet files remain available.

7. Virtual-Lab Experiments

Controlled benchmark scenarios & outcome interpretation

Experiments should change one main factor at a time and compare the result with a baseline. The purpose is to observe the direction and shape of changes in queue depth, throughput, latency, chunk formation, and persistence.

Table 5. Recommended Experimental Scenarios

Scenario Change / Parameter Adjustment Observe / Interpret
Baseline Moderate offered load and default settings. Throughput, queue depth, buffer use, chunks, and persistence.
High load Increase target feed rate gradually. Where actual throughput stops keeping pace; queue and buffer trends.
Slow storage Increase writer delay if supported. Whether persistence lags accepted records and upstream buffers grow.
Queue saturation Reduce queue capacity and raise offered load. Queue policy, producer blocking or drops, and resulting throughput.
Invalid records Increase invalid-record ratio. Rejected count and rejection percentage.
Chunk comparison Run workloads with different chunk sizes. Chunk/file count, bytes, and measured completion delay.

9. Feasibility, Advantages and Limitations

Prototype vs Scalable Target comparison

9.1 Advantages

  • Separates ingestion into understandable, observable stages.
  • Makes queueing, processing, chunking, and persistence visible.
  • Supports controlled workload changes and run comparisons.
  • Stores output as Parquet and tracks metadata locally.
  • Provides a foundation for cloud-storage or distributed-worker extensions.

9.2 Limitations & Scope

Local capacity depends on host hardware. An in-process queue and SQLite store do not establish multi-node durability or distributed consensus. Future extensions require durable brokers and cloud object stores.

Figure 3. Current Local Lab vs Possible Future Extension

CURRENT LOCAL LAB POSSIBLE FUTURE EXTENSION
FastAPI + local engine Multiple API / worker instances
In-process bounded queue Durable broker and replay (Kafka/RabbitMQ)
SQLite metadata Distributed metadata service (PostgreSQL/CockroachDB)
Persistent local Parquet files Cloud object storage (AWS S3 / Backblaze B2)
10

10. Conclusion

Final engineering summary

FlowStore demonstrates the core stages of a time-series ingestion pipeline: generating records, controlling queued work, validating and partitioning records, building chunks, persisting Parquet files, and reporting metadata. Its virtual-lab interface makes these stages easier to inspect and compare under controlled workloads. The local implementation and any future distributed architecture provide different kinds of evidence: local runs demonstrate implemented behavior, while scalability claims require additional testing under realistic deployment conditions.
