1. Abstract

Executive summary of the storage deduplication design

This report presents the design of a storage engine that avoids saving identical data blocks repeatedly. Instead of treating each file as one indivisible object, the engine divides its contents into variable-sized chunks, assigns a SHA-256 identifier to every chunk, and stores only chunks not already present. A file manifest preserves the original chunk order so that a complete file can later be rebuilt and checked for integrity. The course-scale design uses Python, SQLite and a local content-addressed directory. A possible distributed evolution is discussed separately, without claiming that its availability or performance has been demonstrated.

2. Introduction and problem definition

Why whole-file copying wastes capacity and how chunking solves it

Backups and revised documents frequently repeat most of their earlier bytes. Copying an entire file for each revision can consume unnecessary disk space. Whole-file deduplication helps only when two files are completely identical; chunk-level deduplication can also reuse the unchanged regions of partially modified files.

The design challenge is to identify reusable content consistently, maintain reliable references to stored chunks, and reconstruct files exactly even when many versions share the same underlying bytes.

Content-Defined Chunking Implement deterministic content-defined chunking and compare it with fixed-size chunking.

Initial chunker settings are a 4 KiB minimum, 16 KiB target average, 128 KiB maximum and a 64-byte rolling window. These are configurable design parameters, not measured averages. Uploads are assumed sequential and input files are supplied as complete local byte streams on underlying block devices.

4. System architecture

Component stages, pipeline flows, and logical storage models

The proposed local architecture has three main responsibilities: accept file operations, decide which chunks are unique, and persist the data and the information required to rebuild files. Keeping metadata separate from chunk bytes makes the design easier to test and leaves room for a later distributed implementation.

5. Chunking and deduplication design

Rabin rolling fingerprints, SHA-256 integrity, upload and download verification

5.1 Content-defined boundaries

A rolling Rabin-style fingerprint is computed over a moving window of input bytes. After the minimum chunk size, a chosen fingerprint condition can mark a boundary. If no boundary appears, the maximum-size limit forces a cut. Because boundaries depend on content rather than absolute offsets, an insertion near the beginning of a file need not shift all later chunk boundaries.

The rolling fingerprint is only a boundary-selection mechanism. SHA-256 serves a different purpose: naming and verifying the completed chunk. This distinction is essential to the design.

5.2 Upload procedure

  • Read the incoming file incrementally rather than loading the whole file into memory.
  • Emit chunks using the configured minimum, target and maximum sizes.
  • Compute SHA-256 for each chunk and check its existence in the metadata index and chunk store.
  • Reuse a valid existing chunk; otherwise write a new content-addressed chunk file.
  • After required chunks exist, commit the file record, ordered manifest and reference updates in one SQLite transaction.

5.3 Download and verification

For restoration, the system obtains the ordered chunk IDs from SQLite, reads each stored chunk, verifies its SHA-256 digest, and appends the verified bytes in manifest order. The final output is compared against the original file size and whole-file digest. Any missing chunk or checksum mismatch must produce a failed restore rather than a silently incomplete file.

6. Consistency, recovery and deletion

Atomic file renames, temporary chunks, reconciliation, and garbage collection

A SQLite transaction cannot make local filesystem writes atomic. New chunks should therefore be written to temporary files, flushed and renamed into place before completed file metadata is committed. An interruption may leave unreferenced chunk files; a controlled reconciliation pass can find these leftovers. Exact checkpoint-based upload resumption is not assumed.

Deletion must remove file-to-chunk references transactionally. A separate garbage-collection step may remove chunk files only after confirming that no remaining manifest references them. These safeguards are proposed requirements and must be exercised through failure-injection tests before being described as verified.

7. Scalability and future architecture

Distributed scale-out, multi-worker queues, object storage, and coordination

The local prototype is intentionally single-process. A larger deployment could place stateless APIs behind a load balancer, distribute chunking tasks through a bounded queue, use multiple workers, partition the chunk index, and store immutable chunks in object storage. This is a target architecture, not the system evaluated by the course prototype.

Concurrent uploads would require conditional claims or equivalent coordination to prevent multiple workers from independently writing the same new chunk. Replication, crash recovery across nodes, hot-key handling, security and access control would also require separate engineering and experiments.

10. Simulation and system-level analysis

Capacity models, request rates, queues, and latency exploration

A capacity simulation can represent a client, request handler, deduplication engine, metadata service and chunk store. Offered request rate, service time and replica counts can be varied to observe modeled utilization, queue length, throughput and P95/P99 latency. Such results are conditional on the assumptions entered into the simulator; they cannot validate actual CDC behavior, deduplication savings or distributed fault tolerance.

12. Conclusion

Micro-project summary and final takeaways

The proposed engine is a practical System Design Micro-Project because its core behavior can be built and examined using standard development tools. Its strongest contribution is a testable end-to-end path: content-dependent chunking, SHA-256 identity, unique-chunk storage, ordered reconstruction and integrity checking. The distributed design provides a direction for future growth, but reliability, scalability and economic benefit remain unverified until supported by implementation and measured results.
